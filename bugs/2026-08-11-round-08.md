# Round 08 — 2026-08-11

**Lens: the gap between what the code can do and what the user can reach or
see.** Not "is this function correct" but "can a person get to it, and does the
screen tell them what actually happened". Rounds 01–07 read the code; this one
reads the code *from the outside*, the way someone operating the app meets it.

Driven partly against the **live kernel** over marimo's MCP channel (`--mcp
code-mode`), so several claims below are measurements of the running app rather
than readings of its source.

## Findings

### R08-1 — Uploading the same slide twice makes two unrelated slides

`app.py` `_on_upload`:

```python
_tmp = Path(tempfile.mkdtemp(prefix="hescope_upload_")) / _f.name
_tmp.write_bytes(_f.contents)
_open_slide_path(str(_tmp), source_kind="upload")
```

A slide's identity is `UNIQUE(path)` (`SlideRepo.register`). `mkdtemp` returns a
**fresh directory every call**, so uploading `biopsy.svs` twice produces two
slide rows with no relation to each other. Annotations made on the first are
invisible from the second — the panel will say the slide has none.

The path also lives in an OS-managed temp directory, so the row outlives the
file it names.

**Evidence for the consequence, stated precisely.** The live database has 26 of
31 rows on temp paths, 18 of which no longer resolve — but those come from
**tests and probes** (`pytest-of-hp\…`, `hescope_hm_…`, the round-07 scratchpad),
not from this handler: `source_kind='upload'` has **0 rows**, so nobody has ever
pressed the button. The defect is latent, and what those 26 rows demonstrate is
what happens to a temp-path slide row once the directory is gone, which is
exactly the fate an upload is given.

*Class: state outliving its subject; identity derived from an accident.*

### R08-2 — "Add ROI" does not save the ROI anywhere

Measured across the four handlers that touch ROI state:

| handler | session list | `rois` table | patch PNG | `roi_history.jsonl` |
| --- | :--: | :--: | :--: | :--: |
| `_add_roi_or_measure` (**Add ROI**) | yes | — | — | — |
| `_on_send` (**Send to code agent**) | yes | yes | yes | yes |
| `_make_delete`, `_on_clear_rois` | yes | — | — | — |

Everything else in the app reads the **database**: the Statistics panel
(`roi_stats_rows(engine, slide_id)`), all three exports (`export_rois`,
`slide_geojson_text`), and the Annotations editor (`db_roi_rows`).

So an ROI added with the button named "Add ROI" is absent from the statistics,
absent from every export, cannot be labelled, and is gone at the next restart.
The button that *does* save is the one named "Send to code agent".

This is the direct cause of the user-reported confusion in round 08's session:
four outlines drawn on the image, and a sidebar reading "No ROIs yet".

*Class: the label describes the intent, not the effect.*

### R08-3 — A whole-slide sweep's result is discarded on restart; only its settings survive

`set_hm_result` is `mo.state`. There is no heatmap table and no heatmap file.
What *is* persisted is the provenance:

```
interactions.kind='analysis_run'
  {"actor":"human","analysis":"heatmap","metric":"tissue_fraction","tile":256,"downsample":6.646}
```

Payload keys ever recorded: `actor, analysis, bbox, downsample, metric,
nuclei_count, origin, tile`. **No grid, no values.** So the database can tell you
that a sweep ran and with which settings, and cannot tell you what it found.

On the 81671x18211 slide a sweep is minutes of work. Nothing on screen says the
result will not survive the session.

*Class: expensive work with no durable home, and no warning that it has none.*

### R08-4 — QuPath / ASAP annotations cannot be imported at all

`hescope/importers.py` (`import_annotations`, `parse_geojson_annotations`,
`parse_asap_xml`, `ImportReport`) is referenced by **`tests/test_importers.py`
and nothing else** — not `app.py`, not `hescope/cli.py`, not the agent tool list
in `AGENTS.md`. There is no control, no CLI subcommand, and no documented
kernel global.

`docs/ROADMAP-INTEROP.md` presents Tier 1.1 interop as delivered. Export works
(three buttons); import has no door.

*Class: documented capability with no implementation path — the R05-8 shape,
recurring.*

### R08-5 — Three of the four stain-normalisation methods have no way to be selected

`normalize_stain` and `STAIN_METHODS` (macenko, reinhard, ruifrok, vahadane) are
referenced **0 times in app.py**. The display pipeline reaches only
`macenko_normalize`, and only when `refs.stain_source` is set, which no control
sets.

Unlike R08-4 this is *knowingly* unwired: the old checkbox was removed and the
code carries the reason — `macenko_normalize` refits the source matrix from
whatever image it is handed, so a blank background tile normalises to solid
black. Re-wiring needs a slide-level reference matrix, not a checkbox.

**Filed, not fixed.** Recording it so the gap between "four methods implemented
and tested" and "zero methods a user can pick" is visible from the bugs log
rather than only from a comment in the file that removed the control.

## Checked and clean — do not re-file

Both were suspected during this round and both came back negative. Recorded so a
later round spends its time elsewhere.

* **No dead UI controls.** All 39 module-scope `mo.ui.*` controls have either a
  handler (`on_click` / `on_change`), a cross-cell reader, or an in-cell
  `.value` read. An earlier pass in this round flagged five (`file_upload`,
  `path_input`, `zoom_slider`, `label_input`, `notes_input`) — every one was a
  false positive from a check that looked only for `on_click` and for
  *cross-cell* refs. The corrected check finds none.
* **The AGENTS.md contract resolves.** All nine module-scope names promised in
  the tool table are in marimo's graph defs. The `selection_stats` call in the
  §3 example is preceded by its own `from hescope.agent_bridge import
  selection_stats`, and `predict_patch` / `export_rois_geojson` appear
  fully qualified — none of them is a bare call an agent would fail on.
