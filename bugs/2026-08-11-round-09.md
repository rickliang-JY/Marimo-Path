# Round 09 — 2026-08-11

**Lens: what the screen states, versus what is true.** Round 08 asked whether a
user can *reach* a capability. This round asks whether, having used one, the
screen tells them what actually happened — and whether the answer appears
anywhere they are looking.

Two of the four findings were **introduced by round 08's own fixes**, which is
the argument for running the lens at all: moving one store changed what three
readers were describing, and nothing failed.

---

## Findings

### R09-1 — The status strip reports 0 ROIs on a slide that has some

The strip under the viewer counts the **session list**:

```python
_n_rois = len(get_rois())
f"**{_sel_s}** | {_n_rois} ROI(s) this session | ..."
```

R08-2 moved "Add ROI" from that list to the database. The list is therefore
empty in normal operation, so the counter reads `0 ROI(s) this session`
**however many ROIs the user has added** — while the viewer draws every one of
them, because the overlay reads `session + persisted`.

Introduced by round 08, caught in round 09, before either shipped. The regression
test asserts on the whole phrase rather than on `str(n) in text`: a bare
substring check passes by luck against `viewport 1702x820`, which is exactly how
a test comes to pass on broken code.

*Class: a second place re-deriving what one owner decides — the same split that
made the ROIs panel say "No ROIs yet" over four visible outlines.*

### R09-2 — "not added yet" stays on screen after the ROI was added

```python
_sel_s += " — not added yet"
```

Unconditional whenever a selection exists. The selection outline is deliberately
persistent (it is what tells the user *where* they drew), so after a successful
Add ROI the strip goes on describing that exact region as not added. The one
piece of text whose job is to distinguish "drawn" from "saved" gives the same
answer in both states.

### R09-3 — Every sidebar action answers in the other column

`mo.sidebar(...)` makes the left column a separate, independently scrolling
region. It contains the Open-slide panel (Open / Upload / demo), the Display
panel, the Navigator and the ROIs panel — and **no message surface at all**.

Mapped from marimo's graph, writer panel to rendering cell:

| channel | written from | rendered in |
| --- | --- | --- |
| `db_msg` | `loader_panel`, `roi_panel`, agent payload | status strip (main column) |
| `measure_msg` | `loader_panel`, toolbar, ROI cell | status strip (main column) |
| `analysis_msg` | `loader_panel`, heatmap job | Analysis accordion |
| `train_msg` / `train_info` | training job | Analysis accordion |

So "Clear session ROIs" and the per-row Delete — both in the sidebar — report
into a strip under the viewer, and the Open/Upload buttons do the same. The
user-supplied screenshot shows precisely this: the button pressed on the left,
the sentence *"All session ROIs cleared."* rendered in the middle column.

The two message channels do **not** overwrite each other (the strip stacks them
as separate callouts), so this is about distance, not loss.

*Recorded, not fixed: a sidebar message surface is a layout decision, not a bug
fix, and it belongs with round 10's affordance work.*

### R09-4 — The sidebar's per-ROI View / Delete no longer appear for added ROIs

The ROIs panel builds a View and a Delete button per entry of `get_rois()` — the
session list. After R08-2 that list is empty in normal operation, so those rows
never render: the panel shows the saved count and a pointer to the Annotations
accordion instead.

Nothing is lost — the Annotations panel has a selectable table that jumps the
viewer to a row and can delete it — but an affordance moved without the user
being the one who moved it. The panel does say where they went, which is the
minimum; giving them back in place is round 10.

*Consequence of round 08, recorded here so it is not rediscovered later as a
mystery.*

## Checked and clean — do not re-file

* **The empty-state guards on the expensive actions hold.** `_on_analyze`,
  `_on_run_heatmap` and `_on_train` each check for their precondition first and
  write a `warn` — "Open a slide first.", "Training requires the database
  (DB-free mode active)", "Heatmap already running." — rather than failing
  silently or throwing. Round 07's hardening covers them.
* **The status strip does not swallow one message with another.** `measure_msg`
  and `db_msg` render as two stacked callouts in the same cell; neither is
  conditional on the other being absent.
