## R02-2 — `upsert` never backfills a missing `md5sum`, so downloads run unverified

**Severity:** high · **Status:** fixed

`SlideCatalog.upsert` uses `INSERT OR IGNORE`, so an existing `file_id` is left
entirely untouched. That is deliberate for local download state, but it also
applies to `md5sum` — and `md5sum` is the **only** content check a downloaded
slide gets.

The reachable path is the one the class docstring itself documents as
supported: a catalog created before the `md5sum` column existed is upgraded in
place by `ALTER TABLE ... ADD COLUMN md5sum TEXT` at `tcga.py:533`, which fills
every existing row with `NULL`. A later GDC search *does* return `md5sum`
(`search_slides` requests the field, `_record_from_hit` parses it), but
`INSERT OR IGNORE` drops it on the floor. The column stays `NULL` forever.

`app.py:1946` then resolves the expected digest as the table row's `md5sum`
"otherwise look it up in the local catalog by file_id" — and
`tcga_panel.records_to_rows` does not emit `md5sum` at all, so the catalog is
in fact the only source. `NULL` there means `expected_md5=None` reaches
`download_slide`, `_finalize_part` skips the digest branch entirely, and a
100MB–2GB SVS is accepted with nothing on screen to say it was never verified.

**Evidence** — an old-schema catalog, upgraded, then re-searched with the md5
present (`scratchpad/probe_catalog.py`, run against the unfixed tree):

```
after upgrade, md5sum = None
upsert inserted rows: 0
md5sum after re-search: None

fresh row, md5sum = None
md5sum after re-search: None

expected_md5 handed to download_slide(): None
local_path preserved across upsert: /data/tcga/b.svs
```

The same script after the fix:

```
after upgrade, md5sum = None
upsert inserted rows: 0
md5sum after re-search: d41d8cd98f00b204e9800998ecf8427e

fresh row, md5sum = None
md5sum after re-search: 00000000000000000000000000000000

expected_md5 handed to download_slide(): d41d8cd98f00b204e9800998ecf8427e
local_path preserved across upsert: /data/tcga/b.svs
```

**Scope, stated honestly.** The size check is unaffected — the parallel path
still compares against the `Content-Range` total and the legacy path against
`Content-Length` when present. What is lost is exactly what md5 is for:
corruption that preserves the byte count (a flipped range, a truncated-then-
padded resume, a bad disk). It is silent, and it persists for the whole life of
the catalog.

**Fix.** `upsert` follows a no-op `INSERT OR IGNORE` with a narrow `UPDATE`
that sets `md5sum` **only where it is currently `NULL`** and the incoming
record carries one. Existing digests are never rewritten, `local_path` /
`downloaded_at` are untouched, and the returned "newly inserted" count is
unchanged (it still counts inserts only).

**Regression test:** `tests/test_fast_download.py::test_upsert_backfills_missing_md5sum`
builds the pre-`md5sum` schema with the existing `_make_old_schema_db` helper,
upgrades it, re-upserts the same `file_id` with a digest, and asserts both the
column and the value `app.py` would pass as `expected_md5`.
`::test_upsert_never_overwrites_a_recorded_md5sum` pins the other side —
a recorded digest and the local download state both survive a later upsert.

> Note: that second test passes on the unfixed code too, by design. It is a
> guard against the fix overreaching, not a demonstration of the bug.

## R02-3 — server-supplied file name escapes `dest_dir`

**Severity:** low · **Status:** fixed

`_filename_from_headers` returned the `Content-Disposition` filename verbatim,
and both download paths join it straight onto the destination directory —
`tcga.py:384` (`dest = dest_dir / file_name`) and `tcga.py:211`
(`dest_dir / (file_name or f"{file_id}.svs")`). A `../` segment, an absolute
path or a Windows drive letter therefore decides where the slide lands. That
path is also what `mark_downloaded` writes into the catalog and what the
notebook later opens.

**Evidence** (`scratchpad/probe_tcga.py`, unfixed tree):

```
=== _filename_from_headers on hostile Content-Disposition ===
  'attachment; filename="../../../evil.svs"'       -> '../../../evil.svs'
  'attachment; filename="C:/Windows/Temp/evil.svs"'-> 'C:/Windows/Temp/evil.svs'
  'attachment; filename="ok.svs"'                  -> 'ok.svs'

=== download_slide with a traversing filename (legacy, workers=1) ===
  returned: ...\probe-0a_6m4x7\slides\sub\..\..\escaped.svs
  resolved: ...\probe-0a_6m4x7\escaped.svs
  inside dest_dir? False
  file exists at ...\probe-0a_6m4x7\escaped.svs -> True
```

and after the fix:

```
  'attachment; filename="../../../evil.svs"'       -> 'evil.svs'
  returned: ...\probe-ii8mgs_0\slides\sub\escaped.svs
  inside dest_dir? True
  file exists at ...\probe-ii8mgs_0\escaped.svs -> False
```

**Why low.** The real GDC endpoint sends a plain UUID-style `.svs` name, so
nothing in normal operation triggers this — it is latent, in the same sense as
R01-6, and needs a hostile, misconfigured or redirected host (`api_base` is a
constructor argument). The consequence if it ever does trigger is out of
proportion to the likelihood, which is why it is fixed rather than left open.

**Fix.** A new `_contained_name()` keeps the last path component only (after
normalising `\` to `/`), drops anything up to a `:` — `C:evil.svs` is
drive-relative on Windows and joins as an absolute path, and a colon also opens
an NTFS alternate data stream — and returns `None` for `.` / `..` so the
callers fall back to `f"{file_id}.svs"`. It is applied inside
`_filename_from_headers` rather than at the two join sites, so a future third
caller cannot reintroduce the escape by forgetting one. (Round 01's R01-5
lesson: reading for a pattern misses call sites.)

**Regression tests:** `tests/test_fast_download.py::test_filename_from_headers_is_contained`
(8 parametrisations covering `../`, `..\`, absolute POSIX, drive-absolute,
drive-relative, `.`, `..` and an ordinary name) and
`::test_download_stays_inside_dest_dir[1]` / `[4]`, which drive a full
`download_slide` on both the legacy and parallel paths with a traversing
`Content-Disposition` and assert the file lands in `dest_dir` and that nothing
appears outside it.

**Proof the tests fail without the fix** — `hescope/tcga.py` reverted with
`git checkout --`, new tests kept:


## Observations (not bugs)

- **The "already downloaded" shortcut never re-checks md5.** Both paths return
  early when the destination exists with the right size (`tcga.py:212` and
  `:385`), skipping `expected_md5` entirely. Deliberate: re-hashing a 2GB slide
  on every click is a real cost, and `_finalize_part` means a wrong-content
  file cannot get there through the app. Worth revisiting only if a "verify
  existing" button is ever added.
- **`records_to_rows` does not emit `md5sum`**, so `app.py:1946`'s
  `_sel[0].get("md5sum") or <catalog lookup>` always takes the second branch.
  It reads as if the table row could carry the digest. Harmless, and with
  R02-2 fixed the catalog is now the reliable source — but the dead first
  branch invites the belief that the row is a fallback when it never is.
- **RFC 5987 names are not percent-decoded.** `_filename_from_headers` strips a
  `UTF-8''` prefix but leaves the escapes, so `filename*=UTF-8''a%20b.svs`
  lands on disk as `a%20b.svs`. Cosmetic; GDC does not use this form.
- **Legacy retry restarts progress at 0** on each of its three attempts, so the
  bar can jump backwards within the single-stream path. This is the same class
  as round 01's fallback observation, one level down.

## Checked and found clean

- **Parallel progress accounting.** `_fetch` aggregates only newly-written
  bytes and a retry re-requests `bytes={pos}-{end}` — the remainder, never what
  is already on disk. Re-confirmed by
  `test_parallel_download_exact_bytes` (monotonic, ends exactly at total).
- **An ignored `Range` header cannot corrupt the `.part`.** The `!= 206` check
  raises before the file is opened for writing, so a server answering 200 with
  the whole body falls back instead of overwriting a neighbouring worker's
  region.
- **`_finalize_part` gates the atomic rename** on size and then md5, and unlinks
  the `.part` on either failure — `test_expected_md5_wrong_raises` asserts
  neither the final file nor the `.part` survives.
- **`_split_ranges`** covers `[0, total)` contiguously and disjointly, clamps
  `workers` to `total`, and returns `[]` for `total <= 0`.
- **`_resolve_workers`** clamps to 1..16 and falls back to the default on a
  garbage env value.
- **`SlideCatalog._connect`** still opens a short-lived connection per call, so
  the background download thread sharing the catalog with the kernel remains
  safe (re-confirming round 01).
- **`upsert` still preserves local download state** — now pinned by a test
  rather than only by the `INSERT OR IGNORE`.
