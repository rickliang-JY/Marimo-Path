## R05-2 — one file, two slide rows, half the annotations

**Severity:** high · **Status:** fixed (code) / **open** (existing data — see below)

`slides.path` is UNIQUE and is the only thing tying a saved ROI to a file, but
the two production callers spell it differently: `app.py` passed the raw string
from the sidebar text box, `hescope/cli.py` passed `str(f.resolve())`. They can
never agree, so the same file opened under a different spelling became a second
slide row seeing none of the first row's annotations.

**Evidence** (verification pass, four spellings of one existing file):

```
all four name the SAME existing file: True
  register('E:\\...\\assets\\demo_he.png') -> slide id 1
  register('e:\\...\\assets\\demo_he.png') -> slide id 2
  register('E:/.../assets/demo_he.png')    -> slide id 3
  register('assets\\demo_he.png')          -> slide id 4
```

Two of those four involve no user error at all — a pasted path with a lowercase
drive letter, or with forward slashes.

The damage reaches the **documented agent contract**, not just the panel:

```
opened as 'E:\\...\\assets\\demo_he.png' -> slide_id 1
  query_annotations()                    -> [{"id": 1, ... "kind": "rect" ...}]
  get_slide_info()['annotation_count']   -> 1

reopened the SAME FILE as 'E:/.../assets/demo_he.png' -> slide_id 2
  query_annotations()                    -> []
  get_slide_info()['annotation_count']   -> 0
  os.path.samefile(a, b): True
```

**Fix.** `normalize_slide_path()` (`db.py:74`) canonicalizes with
`Path(path).expanduser().resolve()`, falling back to the input string if the
path cannot be resolved. It is applied **inside** `SlideRepo.register` and
`find_by_path`, not at the two call sites, so a future third caller cannot
reintroduce the split — the same reasoning that put `_contained_name` inside
`_filename_from_headers` (R02-3).

Because the code fix cannot heal rows that already exist, round 05 also added
`merge_duplicate_slide_paths(engine)` (`db.py:356`) and exposed it as
`hescope dedupe-slides`: group existing rows by canonical path, lowest id wins,
every other row's ROIs and interactions are re-pointed at the winner.

**Regression tests:** `tests/test_db.py::test_register_dedups_equivalent_spellings_of_one_file`,
`::test_merge_duplicate_slide_paths_reunites_a_split_slide`,
`::test_merge_duplicate_slide_paths_is_a_noop_on_a_clean_database`,
`tests/test_cli.py::test_dedupe_slides_merges_rows_that_name_one_file`.

## R05-4 — the test suite wrote into the user's production data

**Severity:** medium · **Status:** fixed

`hescope.db.get_engine` resolves `url or HESCOPE_DB_URL or DEFAULT_DB_URL`, and
`app.py` calls `bootstrap_db()` with no url. The root `conftest.py` was **0
bytes**, so nothing redirected either the database or
`hescope.paths.resolve_runtime_dir`. The suite drives the real objects on
purpose — `app.run()`, real `ui_actions["send"]` — so it resolved storage
exactly the way a user session does.

**Evidence** — reproduced live during the verification pass's own mandated
baseline run, then pinned causally to one file:

```
$ pytest -q -W "error::FutureWarning"   ->  545 passed, 16 skipped
$ ... count(*) from slides ...          ->  28
  (28, 'C:\\...\\pytest-of-hp\\pytest-234\\slide_b0\\other_slide.png')

before slides: 28
$ pytest -q tests/test_slide_change.py  ->  2 passed
after  slides: 29
  (29, 'C:\\...\\pytest-of-hp\\pytest-235\\slide_b0\\other_slide.png')
```

It was **worse than "only INSERTs into slides"**. Joining `rois` to `slides` in
the shipped database found a past run that had driven the real submit:

```
(6, 20, 'C:\\...\\pytest-of-hp\\pytest-226\\slide_b0\\other_slide.png',
    'E:\\...\\agent_out\\patches\\20260809T172952645101_rect_1000_800_1400_1200.png')
agent_runs: (7, 6, 'roi_submit', 'ok')

An ROI row, an `agent_runs` row and a patch PNG, all written into user data by
`pytest`.

**Fix.** A session-scoped autouse fixture in `conftest.py` sets
`HESCOPE_DB_URL` to a per-session sqlite file and monkeypatches

override for the runtime root by design). Applied from a fixture rather than at
import time, so `hescope.db.DEFAULT_DB_URL` — computed once at import from the
real repo root — keeps meaning what `tests/test_db.py` asserts it means, and
`tests/test_paths.py` still exercises the real function. It also copies the
checked-in demo slide into the session root instead of re-synthesising it.

**Regression tests:** `tests/test_suite_isolation.py` (4). Red with the autouse
marker removed, i.e. `conftest.py` inert as it shipped:

## R05-3 — the interaction trace recorded agents, never humans

**Severity:** medium · **Status:** fixed

`README.md:54` — *"Interaction trace. Selection views, ROI submissions, label
write-backs, tool calls and human-gate decisions all land in the `interactions`
table"* — and `AGENTS.md:154` repeats it. `db.py:133` calls that table the input
to "the data flywheel / automation-bias research". What actually reached it:

```
$ grep -n "interaction" app.py
(no output; exit=1 -- app.py never touched InteractionRepo)

live database, all 6 rows ever written:
  (1,'tool_call',6) (2,'tool_call',6) (3,'tool_call',5)
  (4,'tool_call',5) (5,'tool_call',5) (6,'tool_call',6)
```

Four of the six declared kinds had no writer anywhere in production code. The
sharpest part, verified directly: `label_set` was recorded when an **agent**
wrote a label via `annotate_roi`, and **not** when the human typed one into the
Annotations panel — exactly backwards for the question the table exists to
answer.

> **Correction carried over from the verification pass.** The claim's headline,
> "a real ROI submission traces nothing", is **false**. A real DB-backed submit
> does write an `agent_runs` row with `tool='roi_submit'`; it is the
> `interactions` table specifically that was empty. That is why this is medium
> and not high — the submission itself was never lost.

**Fix.** `DBContext.trace(kind, **fields)` (`viewer.py:415`), with
`InteractionRepo.record`'s contract: never raises, no-op in DB-free mode, so a
UI handler can call it without a `try`/`except` of its own — tracing must never
break the action it is tracing. `app.py` calls it from the four human handlers
(`roi_submit`, `label_set`, `roi_delete`, `analysis_run`), and
`make_live_selection_tool` records `selection_view`. `human_gate` is left
unwritten **on purpose** — there is no human-gate UI — and all three documents
now say so.

**Regression tests:** `tests/test_interaction_trace.py` (9), including
`::test_every_declared_interaction_kind_has_a_writer_except_the_reserved_one`,
which greps app.py + `hescope/*.py` for writes and fails on any declared kind
nothing records. Red without the fix, in three stages:

```

## R05-1 — the GDC `file_id` was joined onto a path unsanitized

**Severity:** low · **Status:** fixed

R02-3 contained the `Content-Disposition` file name; `file_id` arrives from the
same untrusted place (`_record_from_hit`) and was left raw. It is joined onto a
path **twice**: `app.py` builds the per-slide directory as
`TCGA_DATA_DIR / file_id`, and `download_slide` falls back to
`f"{file_id}.svs"`. The traversal therefore applied twice over, and the escaped
path was persisted to `tcga_slides.local_path`.

**Evidence** — end-to-end `download_slide` with only `requests.get` stubbed:

```
requested URL          : https://api.gdc.cancer.gov/data/../../../pwned_by_file_id
download_slide returned: ...\data\tcga\..\..\..\pwned_by_file_id\..\..\..\pwned_by_file_id.svs
resolved               : C:\Users\hp\AppData\Local\pwned_by_file_id.svs
exists                 : True   content: b'hello world'
escaped TCGA_DATA_DIR  : True
catalog local_path     : ...\data\tcga\..\..\..\pwned_by_file_id\...\pwned_by_file_id.svs
```

(the file written outside the sandbox was deleted immediately: `leftovers: []`.)

> **Severity correction, carried over from the verification pass: high → low.**
> The payload rated this high. The capability, reachability and consequence are
> **identical to R02-3**, which this log rates low: `GDC_API` is a hardcoded
> literal with no env override and `app.py` constructs `GDCClient()` with no
> arguments, so it needs a hostile or hijacked `api.gdc.cancer.gov` over TLS.
> When a finding completes an earlier one, its severity inherits from that
> entry unless reachability actually changed. It did not.

**Fix.** `safe_file_id()` (`tcga.py:438`) routes the id through R02-3's
`_contained_name`, falling back to `"unknown_file_id"`. Applied inside
`download_slide` **and** at app.py's join site, because the app builds the
directory itself.

**Regression tests:** `tests/test_fast_download.py::test_safe_file_id_is_contained`,
`::test_download_contains_a_traversing_file_id[1]`/`[4]`, and
`tests/test_notebook_wiring.py::test_the_tcga_download_contains_the_server_supplied_file_id`,
which asserts over marimo's own graph that **every** `TCGA_DATA_DIR / x` join in
the download cell has `x == safe_file_id(...)` — a rename cannot leave it
passing on unwired code. Red without the fix:

## R05-7 — `init_db` never added missing columns

**Severity:** low · **Status:** fixed

`init_db` was `Base.metadata.create_all(engine)`, which adds missing TABLES but
never missing COLUMNS. Against a database written by a build with a narrower
schema:

```
bootstrap_db -> enabled: True   error: None
tables after init_db: ['agent_runs', 'interactions', 'rois', 'slides']  <- missing TABLE created
rois columns after init_db: [... unchanged ...]                          <- missing COLUMN not
roi add RAISED: OperationalError: table rois has no column named magnification
```

The failure mode is the bad one: `db.enabled` stays True so no DB-free callout
appears and every panel looks live, but each save answers "Submit failed". And
`AgentBridge.submit` persists **before** appending to `roi_history.jsonl`, so a
failed row means no history line either — the ROI is gone entirely.

The project had already solved this for the TCGA catalog (`PRAGMA table_info` +
`ALTER TABLE`) and not for the database holding the user's annotations.

**Fix.** The same additive upgrade in `init_db` (`db.py:112-128`): additive only
— never a drop, a rename or a type change — and columns are added without NOT
NULL, which SQLite rejects on `ADD COLUMN` without a default. A failure
propagates to `bootstrap_db`, which degrades to DB-free mode: an honest
"database disabled" beats a live-looking panel.

**Regression test:** `tests/test_db.py::test_init_db_adds_columns_an_older_database_is_missing`.
Red without the fix:

```
E   AssertionError: assert 'magnification' in {'bbox_json', 'created_at', 'id', 'kind', ...}
1 failed in 1.08s
```

## Observations (not bugs)

- **R05-6 was rejected as a finding, deliberately.** The claim was that
  `InteractionRepo.for_slide` returns the OLDEST N rows, silently truncating at
  `limit=200`. The behaviour reproduces exactly — 200 rows returned, payloads
  `{"i": 0}` .. `{"i": 199}` out of 250 recorded — but the method's own
  docstring is *"Interactions for one slide, oldest first"*, `recent(limit,
  kind)` covers the descending direction, and there was no caller anywhere. An
  API gap, not a defect. **It becomes a real bug the moment a panel starts
  reading it**, which R05-3's new writers make likely: `for_slide` now has real
  data to truncate. The number is retired, not reused.
- **A severity-calibration note for later rounds**, which is why R05-1's
  correction is spelled out above: when a finding *completes* an earlier one,
  its severity should inherit from that entry unless reachability actually
  changed.
- **`records_to_rows` still does not emit `md5sum`** (round 02's observation),
  so `app.py`'s `_sel[0].get("md5sum") or <catalog lookup>` still always takes
  the second branch.
