## R06-1 — the feature vector is raster-dependent, and nothing matched the two rasters

**Severity:** high · **Status:** fixed

`features.extract_features` is raster-dependent by construction:
`nuclei_count`, `nuclei_mean_area_px` and `blur_score` are pixel-geometry
quantities. Training patches come from `rois.extract_patch`, capped at 1024 px
(`rois.py:110`); heatmap tiles are `hm_tile_slider` px at
`_ds = max(1.0, max(w, h) / (tile * 48))` (`app.py:2557`), which is 3-8 for any
40k-100k px slide. The two rasters therefore never agree by accident on a real
WSI. `meta.json` recorded no raster and `_feature_vector_for_model` did no
resize, so nothing could even detect the mismatch.

Round 01 recorded this area clean — *"`ml.py` … reuses the same feature path at
predict time, avoiding train/inference feature mismatch"*. The same *function*
is reused; the same *raster* was not.

**Evidence** — identical pixels, only the raster differs
(`.venv/Scripts/python.exe -c` over `_feature_vector_for_model`, rasters
1024 / 512 / 256 / 128):

```
== NO-FIX
  nuclei_count                34.0000    33.0000    32.0000    32.0000
  nuclei_mean_area_px       4973.6763  1263.1818   325.5000    80.7188
  blur_score                 489.5560   412.1961   756.7109  1491.6411
  tissue_fraction              0.1615     0.1596     0.1582     0.1447
```

End to end, through a real model trained at `extract_patch`'s 1024 px cap and
then asked to score the SAME pixels as a tile (`scratchpad/probe_e2e.py`):

```
$ python scratchpad/probe_e2e.py           # before the fix
trained dim 56 raster 256
P(dense) on dense  : 1024=0.9785  512=0.9982  256=0.9994  128=0.9997
P(dense) on sparse : 1024=0.0165  512=0.2942  256=0.5559  128=0.5812
```

A patch that IS sparse scores P(dense)=0.0165 at the training raster and
0.5559 as a 256 px tile — **the class flips on pure resampling**. The heatmap
was being decided by tile geometry rather than by the tissue.

**Fix.** `hescope/ml.py` grows `FEATURE_RASTER = 256` and normalizes *both*
ends of the handcrafted path to it: `_load_feature_vector` resamples every
training patch, `_feature_vector_for_model` resamples every tile, and the
raster is recorded as `feature_raster` in `ModelInfo` and `meta.json` (so
`list_models`, and therefore the agent-facing `get_analysis_capabilities()`,
now report it). A meta *without* the key is scored exactly as before — models
trained earlier were fit at whatever raster their patches happened to have, so
resampling those would introduce the very mismatch this removes.

The encoder path is deliberately untouched: `Encoder.preprocess` already
resizes to 224x224 (`embeddings.py:196`), so `feature_raster` is None there.

After the fix, same probe:

```
P(dense) on dense  : 1024=0.9792  512=0.9745  256=0.9735  128=0.9922
P(dense) on sparse : 1024=0.0185  512=0.0230  256=0.0199  128=0.0254
```

Two things the fix does **not** claim to solve, stated so a later round does
not read more into it:

* **Field of view.** A 1024 px ROI patch covering 2048 level-0 px and a 256 px
  tile covering 256 level-0 px still see different amounts of tissue. Only the
  per-pixel raster is matched; matching the FOV would mean changing the sweep
  geometry, not the feature call.
* **`blur_score`.** A tile that really was read at 128 px *is* blurrier, and no
  resampling puts the detail back. That is information loss, not a raster
  artefact, and the regression test says so explicitly.

Secondary benefit, measured (`scratchpad/cost.py`), which is also most of
R06-7's cost:

```
  256 px patch: at its own raster    34.6 ms | normalized to 256    38.2 ms
  512 px patch: at its own raster   142.2 ms | normalized to 256    41.7 ms
 1024 px patch: at its own raster   612.1 ms | normalized to 256    57.3 ms
```

**Regression tests:** `tests/test_feature_raster.py` (9 tests) —

## R06-2 — a sweep in which every tile failed was reported as a success

**Severity:** medium · **Status:** fixed

`compute_grid` wrote `np.nan` for a tile whose metric raised — the same `NaN`
a tile skipped by the tissue filter gets — and `render_heatmap` blends only
non-NaN cells. A totally failed sweep is therefore **byte-identical to the bare
thumbnail**. `_work` then wrote its success message unconditionally after
`compute_grid` returned and the ticker rendered it as a green
`mo.callout(kind="success")` (`app.py:2748`) above a caption reading
`metric model_prob:tumor | grid 2x3`. Total failure was presented exactly as
"no tissue here".

**Evidence** — app.py's REAL "Run heatmap" button, a REAL trained model whose
meta names an encoder that cannot be loaded (the state a model directory
reaches when it is copied to a machine that cannot fetch the weights, or during
a torch-hub / HF outage), no production code patched:

```
E  AssertionError: a sweep in which every tile failed was reported to the user
   as 'success': "Heatmap 'model_prob:tumor': grid 3x4 (tile 256, downsample
   1.00).". The image below it is the bare thumbnail, so a broken model is
   indistinguishable from empty background.
```

and the mechanism, at the hescope level:

```
assert np.array_equal(np.asarray(render_heatmap(thumb, grid)), np.asarray(thumb))
```
passes for an all-failed grid — the overlay is literally the input image.

**Fix.** `compute_grid` gains `error_cb(gx, gy, exc)`, called for every tile
whose metric raised (skipped tiles do not call it — that distinction is the
whole point). `_work` counts the failures and keeps the first message, then
picks the message from what actually happened:

* every tile failed → `danger`, naming the count and the first error;
* some tiles failed → `warn`, `"N of M measured tiles failed and are blank"`;
* nothing passed the tissue filter → `warn`, `"no tile passed the tissue
  filter, so nothing is overlaid"`;
* otherwise → `success`, now also reporting how many cells were measured.

The valid-cell count is `sum(1 for _v in _grid.flat if _v == _v)` — NaN != NaN
— so no numpy import is added to the notebook.

**Regression tests:** `tests/test_heatmap_failure_report.py` (4) —
`::test_compute_grid_reports_the_tiles_whose_metric_raised`,
`::test_a_skipped_tile_is_not_reported_as_a_failure`,
`::test_a_totally_failed_sweep_renders_as_the_bare_thumbnail`,
`::test_the_button_reports_a_totally_failed_sweep_as_a_failure`.

Red in two stages, so each half of the fix is pinned separately. With only
`_work`'s message reverted to the unconditional success (`error_cb` still
present): 1 failed, 3 passed, output quoted above. With `error_cb` removed from
`compute_grid` as well: 3 failed, 1 passed.

## R06-4 — the encoder-fallback warning never reached the UI

**Severity:** medium · **Status:** fixed

`_on_train` built `set_train_info` from a fixed key list — name, labels,
n_samples, cv_accuracy, feature_dim — and then wrote
`("success", "Model '<name>' trained.")`. Neither `warning` nor `encoder` was
in that list, although `ModelInfo` carries both and `meta.json` stores both.
The whole point of `HESCOPE_EMBEDDER` is to swap 56 handcrafted numbers for
1024-d pathology foundation-model embeddings; a user who follows
`docs/STRATEGY.md` and sets it got the handcrafted model with a green success
message, with only `feature_dim: 56` buried in a table as a checksum nobody
reads that way. This is not only the mistyped-env-var case: the platform's own
documented default encoder `gpfm` 404s on Hugging Face today and falls back the
same silent way.

**Evidence** — app.py's REAL "Train from annotations" click with
`HESCOPE_EMBEDDER=gpfm_typo_r06`, labelled ROIs in the notebook's own database,
against the pre-fix message construction:

```
E  AssertionError: HESCOPE_EMBEDDER could not be loaded and training silently
   fell back to handcrafted features, but the user was told 'success':
   "Model 'r06_warn' trained."
E  assert 'success' == 'warn'
```

and, on the normal path, `KeyError: 'encoder'` — the info table never said
which feature space the model lives in.

**Fix.** `_on_train` puts `encoder` (`_info.encoder or "handcrafted"`) in the
info table beside `feature_dim`, and surfaces `_info.warning` as a `warn`
callout reading `Model '<name>' trained, but: <warning>` instead of the
unconditional success. The information already existed two layers down; only
the last hop was missing.

**Regression tests:**
`tests/test_train_job.py::test_a_failed_embedder_is_reported_instead_of_a_green_success`,
`::test_the_info_table_names_the_feature_space_on_the_normal_path`.

Red with the pre-R06-4 info dict and message restored (worker thread kept, so
the failure is about the message and not about R06-7):
`2 failed, 2 passed in 18.36s`.

## R06-3 — a class lost to missing patches disappeared silently

**Severity:** low · **Status:** fixed

`agent_out/patches/` is scratch output while the `rois` rows are the durable
record, so the two drift apart in normal use (a cleanup, a moved repo, a tmp
reaper), and a row labelled in the Annotations panel never had a patch at all.
`train_from_annotations` skipped those rows — documented in its docstring — but
recorded nothing: a three-class model became a two-class model with
`ModelInfo.warning` still None, `model_prob:necrosis` quietly vanished from the
heatmap metric dropdown, and every tile that was really necrosis was forced
into one of the two survivors.

Downgraded from the claim's medium because the skip is documented and the
surviving label list *is* displayed in the train-info table, so the outcome is
visible even though nothing flagged it. The gap is that `ModelInfo.warning` —
which exists for exactly this kind of note and is threaded all the way to
`meta.json` — was left at None.

**Evidence** — three classes of three ROIs, only the three necrosis PNGs
deleted (DB rows untouched), plus one tumor ROI labelled in the panel and never
submitted. Against the pre-fix code the model silently loses a class:

```
E  AssertionError: a whole labelled class was dropped from the model and
   nothing recorded it -- ModelInfo.warning, which exists for exactly this
   kind of note and is threaded all the way to meta.json, stayed None
E  assert (None is not None)
E   +  where None = ModelInfo(name='m3', labels=['a', 'b'], feature_dim=16,
        cv_accuracy=1.0, n_samples=6, ..., warning=None, feature_raster=256).warning
```

**Fix.** `train_from_annotations` counts the skipped rows per label and records
them in `ModelInfo.warning` (joined with the embedder warning when both apply),
naming any label that lost *all* its patches. The same scenario after the fix:

```
labels : ['stroma', 'tumor']
warning: 4 labelled ROI(s) skipped (no usable patch image): 'necrosis' (3),
         'tumor' (1); no usable patch left for 'necrosis' -- that label is NOT
         in this model
```

"no usable patch image" covers both causes — a row that never had a
`patch_path` and one whose file is gone — because both are equally invisible in
the trained model and the message must not claim a file was deleted when none
ever existed. R06-4's fix is what puts this in front of the user.

**Regression tests:**
`tests/test_ml.py::test_a_label_lost_to_missing_patches_is_recorded_in_the_warning`,
`::test_missing_patches_that_lose_no_class_are_still_counted`.
Red with the note removed (`warning = embedder_warning`): `2 failed, 5 passed`.

## R06-7 — training froze the kernel

**Severity:** low · **Status:** fixed

`app.py`'s own heatmap cell documents why inline work is unworkable
(`app.py:2494-2508`: *"marimo resolves state updates only after the runner
finishes … no cell could re-render while the handler was on the stack"*) and
round 04 moved the sweep to `hm_job` + a ticker for exactly this reason
(R04-6). Training was left behind: `_on_train` called
`train_from_annotations` on the stack, so a realistic annotation set froze the
whole notebook with no progress bar and no message. Measured before the fix:
**19.73 s for 20 labelled ROIs**, i.e. ~1 s per ROI, extrapolating to ~99 s for
100 ROIs.

Note the claim's second half — "no in-flight guard, so a second click starts
the work again" — was **not verifiable**: while the kernel is blocked a second
click cannot execute concurrently. The finding stood on the freeze alone; the
guard below is a consequence of the thread move, not a claimed defect, and is
pinned by its own test.

**Fix.** The same shape as `hm_job`: a plain `train_job = {"thread", "result",
"msg"}` dict in the analysis-state cell, a worker thread started by
`_on_train`, and the **existing** 1 s ticker cell drains it on the main thread
(publishing `set_train_info` / `set_train_msg` and bumping
`set_models_version`). One ticker rather than a second one — a `mo.ui.refresh`
widget must not be displayed from two cells, and the training hand-off needs
nothing the heatmap hand-off does not already have.

Two details that are not obvious:

* `set_train_info(None)` is called on the **main thread** at click time, so a
  failed run cannot leave the previous model's table standing under its error
  message; the worker only ever *publishes* a result.
* `set_models_version(object())` moved into the ticker, because a state setter
  called from a foreign thread is inert. `hm_tile_slider` and `hm_nav_checkbox`
  are still outside its closure, so R04-4 does not regress
  (`test_sweep_controls_are_not_rebuilt_by_a_training_run` still passes).

Cross-thread SQLite was checked rather than assumed: SQLAlchemy 2.0.51 opens
file-based sqlite with `QueuePool`, and a read from a worker thread through the
same engine succeeds.

**Regression tests:**
`tests/test_train_job.py::test_the_click_returns_before_the_training_does`
(self-calibrating, like R04-6's: if training runs inline the join is free and
the click IS the total) and
`::test_a_second_click_is_refused_while_training_is_in_flight`.

Red with `_work()` called inline and the guard removed:

```
E  AssertionError: training never started
E  assert None is not None
FAILED ...::test_the_click_returns_before_the_training_does
FAILED ...::test_a_second_click_is_refused_while_training_is_in_flight

## Observations (not bugs)

- **REFUTED by the verification pass, recorded so it is not re-filed.**
  *R06-5* claimed `nuclei_density` is a raw count on a <=256 px thumbnail.
  Both halves it calls a defect are documented design
  (`docs/USER_GUIDE.md:261`: *"nuclei count per tile, automatically downsampled
  for large tiles to control cost"*), and the claimed 5.7x
  tile-size spread measured **1.62x** over 77 identical level-0 512x512
  squares. The 84%-loss figure is real but only at effective downsample 8
  (rasters 2048→128 gave 2422/1751/1041/373/72 nuclei), which needs a
  ~98,000 px slide at tile 256. Worth knowing anyway: a 49,152 px WSI does
  reach ds=4, i.e. 43% recovery, and per-cell value ranges are not comparable
  between sweeps (tile=128: 1..20, tile=256: 11..66, tile=512: 71..135).
- **REFUTED.** *R06-6* claimed `analysis_capabilities` reports a default
  encoder of `gpfm` while the handcrafted path is active. The key sits inside
  `available_encoders`, whose siblings are `torch_importable` and the registry,
  and `default_encoder_name()` documents itself as *"Default encoder under the
  license red line"* — which encoder would be picked, not which is in use. The
  same report carries each model's own `encoder` and `feature_dim`. Naming nit
  at most. (`AGENTS.md:61` documenting three top-level keys while four are
  returned is the already-recorded R02-4, still unfixed, not a new finding.)

  `default_encoder_name()` filters on `commercial_ok and not gated`, `uni2h` is

  that would have asserted it assert on message *content* instead, with a

  coincidence, not a design.
- **Re-synthesising the demo slide is expensive and racy.**
  `generate_demo_slide("assets/demo_he.png")` regenerates a 6000x4000 PNG
  unconditionally (~15 s, a 275 MiB float32 allocation) and writes it into the
  repo. `defs["ensure_demo_slide"]()` resolves under the session runtime root
  and reuses the cached copy. Two concurrent pytest processes on this machine
  hit `numpy._core._exceptions._ArrayMemoryError` in that allocation — which is
  also why round 06's verification pass saw `OSError: image file is truncated`
  against that asset.
