## R04-1 — the Annotations panel is rebuilt by every pan and zoom

**Severity:** high · **Status:** fixed

The annotation-browser cell took `get_vp` into its signature — added by R03-3's
own fix, so its row-click handler could read `get_vp().size` and build the jump
target. `get_vp` is the `State` object marimo matches on, so
`resolve_state_updates` condition 5 re-runs every cell that has it among its
refs; `set_vp` fires on any real mouse gesture (the widget reports past a
0.5 viewport-px / 1% zoom threshold, `osdviewer.py:857-881`, consumed at
`app.py:1350`). Rebuilding is not harmless: marimo stamps every constructed
element with a fresh random token **on purpose**, so "re-running a cell that
creates a UI element will trigger a re-render and reset it to its initial
value" (`marimo/_plugins/ui/_core/ui_element.py:200-205`).

The annotation editor is downstream of the browser (it reads
`annotation_table.value`), so `label_input` and `notes_input` went with it.

**Evidence** — marimo's own `DirectedGraph` over app.py's compiled cells, the
roots being condition 5 and the closure being everything downstream
(`scratchpad/fanout3.py`; skipping the runtime's "setter cell" and "already ran
after" exclusions only makes the real set smaller, so the reading is
conservative):


`Kclp` is in the closure too — that is the cell computing `selected_index`,

**Why high.** app.py documents this exact invariant twice and enforces it
everywhere else — `app.py:923` ("THIS CELL MUST NOT REFERENCE get_vp ... a

OpenSeadragon cell's "*** THIS CELL'S DEPENDENCY SET IS LOAD-BEARING ***". The
one panel holding user-**typed** data broke it. On the default surface,
labelling is unusable: touch the slide and the selection, the highlight and the

**Fix.** The jump becomes a named action, exactly like every toolbar control

`ui_actions["jump_bbox"]` (`:1084`); the browser's row handler looks it up at
click time (`ui_actions` is a notebook global, so it survives cell-private name
mangling — the R01 trap). The browser cell's signature drops `dc_replace`,
`get_source`, `get_vp`, `jump_viewport_for_bbox` and `move_camera` and is now
`(db, db_roi_error, db_roi_rows, get_slide_id, mo, ui_actions)`.

## R04-2 — a new slide inherits the previous slide's ROIs and payload

**Severity:** high · **Status:** fixed

`_open_slide_path` (`app.py:439`) reset `source`, the measurement readout, the
viewport, `viewer_bus["vp"]`/`["sel_seq"]`, the tile source and `slide_id` — but
never `get_rois`, `get_payload`, `get_hm_result` or `get_analysis_result`. All
four hold bare level-0 geometry or level-0 pixel statistics with no record of
which slide they came from.

`_on_send` reads `_rois = get_rois()` and falls back to the live selection only
when that list is **empty**, then submits `_rois[-1]` against the currently open
source. `_on_analyze` falls back to `get_payload()` and then to
`get_rois()[-1]`, reporting origin "last submitted ROI".

**Evidence** — driven end to end through `app.run()`'s real objects: the real
`open_slide_path` (the same function the sidebar, the upload box and the TCGA
panel call) and the real `ui_actions["send"]` toolbar action
(`scratchpad/before.py`, unfixed tree):

```
slide A: demo_he.png (6000, 4000)
slide B: small_slide.png (600, 400)
  get_rois()           -> [('rect', (1000, 800, 1400, 1200))]
  get_payload()        -> None
  get_hm_result()      -> GRID-A
  get_analysis_result()-> ('ok', 'last submitted ROI', {'bbox': [1000, 800, 1400, 1200]})
  live_selection() on B-> None
  after 'Send to code agent' with nothing drawn:
    ('success', 'Sent ROI to agent: rect bbox=[1000, 800, 1400, 1200] — the agent
      reads it with get_latest_selection().')
```

The last line is the whole finding: nothing was drawn on slide B, and the app's
most prominent green button reports success over slide A's rectangle. That
submit writes a row into the `rois` table under slide B's id, saves a patch PNG
and appends to `agent_out/roi_history.jsonl`.

**Why high.** Silently wrong data in three places a code agent reads. Here the
bbox lands entirely off slide B so the statistics are white padding
(post-R03-1 behaviour, correct in itself); **two large slides is the worse
case**, because the coordinates then land on real but unrelated tissue and
nothing looks anomalous.

**Fix.** `_open_slide_path` clears them in the same place it already clears the
measurement and the de-dup bookkeeping (`app.py:443`):

```python
set_rois([])
set_payload(None)
set_analysis_result(None)
set_analysis_msg(None)
set_hm_result(None)
```

Adding the setters costs no reactivity: a setter name is not the `State` object
marimo matches on, so the loader cell gains no re-run triggers.

Same probe, after:

```
  get_rois()           -> []
  get_payload()        -> None
  get_hm_result()      -> None
  get_analysis_result()-> None
  after 'Send to code agent' with nothing drawn:
    ('warn', "Nothing to send: drag a box or lasso on the viewer first (or click 'Add ROI').")
```

**Regression tests:** `tests/test_slide_change.py::test_a_new_slide_does_not_inherit_the_previous_slides_session_state`

## R04-3 — the heatmap grid is blended onto the next slide's thumbnail

**Severity:** medium · **Status:** fixed

Same missing reset, one level down. The navigator cell (`app.py:708-746`)
blends `get_hm_result()["grid"]` over the current slide's thumbnail whenever
`hm_nav_checkbox` is on, guarded only by `except Exception: pass  # stale/
mismatched grid`. A grid from **another slide** does not raise — `render_heatmap`
simply resizes it — so the guard never fires. Worse, R03-4's own `grid_coverage`
fix then computes coverage from the NEW slide's dimensions against the OLD
slide's grid shape, tile and downsample, producing a confident registration
that means nothing.

The setup is reachable because the navigator cell re-runs on `set_source` while
the cell owning `hm_nav_checkbox` does not, so the user's "show heatmap on
navigator" choice survives the slide change.

**Evidence** — the `GRID-A` line in R04-2's probe above is the same measurement
(`get_hm_result()` survives the slide change) taken through the real
`open_slide_path`. The Analysis accordion likewise kept showing slide A's PNG
and its "metric ... | grid 16x24" caption while slide B was open.

**Why medium.** This is R03-4's failure mode — a metric drawn off the tissue it
was measured on — but a whole slide out instead of one cell out, and it is
invisible: the thumbnail looks like a plausible heatmap.

**Fix.** `set_hm_result(None)` and `set_analysis_msg(None)` in
`_open_slide_path`, i.e. the same change as R04-2. One fix closes both.

**Regression test:** the `get_hm_result() is None` assertion in
`tests/test_slide_change.py::test_a_new_slide_does_not_inherit_the_previous_slides_session_state`
(red in the run quoted under R04-2).

## R04-4 — training resets the tile-size slider and the navigator checkbox

**Severity:** low · **Status:** fixed

The heatmap-controls cell read `get_models_version()` only to refresh
`hm_model_dropdown` after training, but it also built `hm_tile_slider` and
`hm_nav_checkbox`. `_on_train` ends with `set_models_version(object())` on the
success path, so a successful train re-ran the cell and re-constructed all
three — and a re-constructed element comes back at its default.

**Evidence** — marimo's own graph, before the fix:

**Why low but worth fixing.** Small and visible, but it is the toolbar lesson

## R04-5 — "Add ROI" in measure mode erases the measurement it just made

**Severity:** low · **Status:** fixed

> **Correction in place — the handed-in claim was partially refuted.** It was
> submitted as "17 lines of dead branch: the measure branch of `_on_add_roi` is
> unreachable". That is **false**, and the verification pass reproduced the
> branch executing. The widget does not clear its `selection` trait when the
> tool changes (`osdviewer.py` binds `change:tool` to `applyTool`, which only
> touches gesture settings and the cursor), so a rect drawn *before* measure
> mode was switched on is still what `live_selection()` returns and the branch
> runs on it. The branch could therefore not simply be deleted. What is real
> is the symptom underneath, and it is worse than "dead code": the warning and
> the measurement share the one `set_measure_msg` channel.

`parse_osd_selection` refuses `kind="measure"` on purpose — `_ROI_KINDS =
("rect", "polygon")`, `osdviewer.py:889/945` — because a measurement is a UI
readout and must never reach the agent contract as an ROI. `_on_add_roi` only
ever asked `live_selection()`, which is therefore `None` during a measurement,
and its no-selection branch writes a warning into the same channel the widget's
report cell had just published the measurement on.

**Evidence** — the real widget and the real toolbar action through `app.run()`
(`scratchpad/before.py`, unfixed tree):

```
measure_checkbox.value: True
raw widget value selection: {'kind': 'measure', 'points_level0': [[100.0, 100.0], [500.0, 400.0]], 'seq': 1}
live_selection() -> None
status line before the click: ('info', '400.0 x 300.0 px')
status line after  the click: ('warn', 'No selection: drag a box or lasso on the viewer first.')
```

The measurement the user just took is destroyed and replaced by a statement
that contradicts what they did.

**Why low.** Not a data-integrity bug — nothing wrong reaches the DB or an
agent. It is filed because it is the third instance of the shape that produced
the three dead toolbar buttons: a handler reasoning about a surface whose
vocabulary it cannot see.

**Fix.** A companion to `live_selection()` in the same surface-arbiter cell:
`live_measure()` (`app.py:1428`) returns the level-0 corners of a measure drag
on the OpenSeadragon surface, falling back to a rect selection — which covers
both the plotly surface (no measure tool exists there; a box selection *is* the
measurement) and the stale-rect case above. `_on_add_roi` now takes the measure
branch **first**, off `live_measure()`, so the generic "No selection" warning
can no longer fire during a measurement. With nothing measurable the click
still gets an answer, now one that names measure mode.

**Regression tests:** `tests/test_measure_mode.py` — four tests, two pinning
the bug and two guarding against the fix overreaching. Red with the old branch
restored:


## R04-6 — the heatmap sweep runs inside the click handler

**Severity:** low · **Status:** fixed

`_on_run_heatmap` set `set_hm_progress((0,1))`, fed
`progress_cb=lambda _d,_t: set_hm_progress((_d,_t))` into `compute_grid`, and
always ended with `set_hm_progress(None)` in a `finally`. marimo resolves state
updates only **after** the runner finishes (`marimo/_runtime/runtime.py:1561-1566`:
`await runner.run_all()` and then `runner.resolve_state_updates(...)`), so no
cell could re-render while the handler was on the stack, and by then the
coalesced value was always `None`. Two things that look functional were
therefore impossible: the `if _prog is not None:` progress block never
rendered, and the `get_hm_progress() is not None` in-flight guard could never
be true.

**Evidence** — the real "Run heatmap" click through `app.run()`
(`scratchpad/hm_timing.py`, unfixed tree, 6000x4000 demo slide):

```
metric: nuclei_density
click BLOCKED for 9.15 s
get_hm_progress() when the click returns: None
analysis msg: ('success', "Heatmap 'nuclei_density': grid 16x24 (tile 256, downsample 1.00).")
second click msg: ('success', "Heatmap 'nuclei_density': grid 16x24 (tile 256, downsample 1.00).")
```

The second click re-ran the whole sweep instead of hitting the guard, because
the `finally` had already restored `None`. (`tissue_fraction` on the same slide
blocks 0.4 s; the drama belongs to WSI-sized slides — round 03's
81671x18211 slide plans an 11x48 = 528-cell sweep.)

**Fix.** The shape the app already ships and documents for the TCGA download:
a worker thread, a plain non-reactive dict, and a ticker cell that renders
progress and publishes the result on the main thread.

* `hm_job = {"thread", "progress", "result", "msg"}` and a 1s
  `hm_ticker` in the analysis-state cell (`app.py:355`);
* `_on_run_heatmap` (`:2430`) resolves the metric **synchronously** — "select a
  model first" is a user error about the controls and must be answered now, not
  a tick later — then starts a daemon thread and returns;
* a ticker cell (`:2527`) consumes `hm_job["result"]`/`["msg"]` into `mo.state`
  and renders the bar. It is a cell of its own, and `hm_progress_view` is
  stacked next to `heatmap_view` in the Analysis accordion rather than inside
  it, so the once-a-second re-render does not drag the heatmap PNG through a
  fresh base64 data URI every tick;
* `get_hm_progress` / `set_hm_progress` are deleted rather than left as a
  channel nothing can observe.

Same probe, after:

```

click BLOCKED for 0.00 s
total (click + worker) 7.81 s   click share 0.0097%
job progress after join: None
job msg after join     : ('success', "Heatmap 'nuclei_density': grid 16x24 (tile 256, downsample 1.00).")
job result after join  : ((16, 24), {'metric': 'nuclei_density', 'tile': 256, ...})
```

**Regression tests:** `tests/test_heatmap_job.py` — the click must return
before the sweep does (self-calibrating: it compares the click against
click+join, so it needs no hardcoded budget), progress must actually move while
a sweep is in flight, a second click must be refused, and a control error must
still be answered immediately with no worker started. Red with the sweep put
back inline (`hm_job` and the ticker cell kept, the body de-nested — the exact
state the fix changed):

## Observations (not bugs)

- **The heatmap worker is a second unsynchronised reader of `SlideSource`.**
  The tile server serialises `read_region` per slide behind a `read_lock`
  (`tileserver.py:548-555`) because `TifffileSource._zarr()` mutates per-level
  caches without synchronisation; a heatmap thread reads outside that lock. The
  window it protects is already closed for any slide the OSD path opened:
  `TileServer.register` pre-warms **every** level with
  `source.read_region((0, 0), lvl, (1, 1))` in the calling thread
  (`tileserver.py:662-666`) before the widget exists. `openslide` is documented
  thread-safe per handle and `PillowSource` slices an in-memory array. If a
  future `SlideSource` builds state lazily and is not pre-warmed, this is where
  it will bite; the durable fix would be to move the lock onto the source.
- **A second always-on 1s ticker.** `hm_ticker` joins `tcga_ticker` in never
  idling, which extends round 01's observation rather than answering it. It is
  what makes the progress bar possible at all, and the refresh control is
  rendered so a user can slow or stop it. Gating a ticker on "a job is running"
  needs the ticker to be rebuilt, which resets it — worth solving once, for
  both.
- **`hm_progress_view` sits below the heatmap image, not below the button.**
  That is a layout compromise made to keep `heatmap_view` out of the 1s
  re-render path; splitting the result image into its own cell would allow the
  progress bar to sit where it belongs.
- **The Analysis accordion must be open for a sweep to complete.** The ticker
  publishes `hm_job["result"]` into `mo.state`, so if the panel is collapsed
  and the ticker stops firing, the finished grid lands when it is re-opened.
  Self-healing, and the same limitation the TCGA download already has.
- **`_open_slide_path` does not reset `get_db_msg`.** Deliberate: it writes
  into that channel itself, later in the same function, for a tile-server
  failure. The message is generic ("Slide registration failed: ..."), not
  slide-scoped data, so it is out of R04-2's scope.
