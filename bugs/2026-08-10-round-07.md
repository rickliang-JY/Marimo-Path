## R07-1 — a heatmap sweep that outlived its slide was published onto the next one

**Severity:** high · **Status:** fixed

R04-3 closed "slide A's heatmap blended onto slide B's thumbnail" by clearing
`set_hm_result(None)` inside `_open_slide_path`, i.e. **at OPEN time**. R04-6
then moved the sweep onto a worker thread, and a worker writes
`hm_job["result"]` / `hm_job["msg"]` *after* that clear. The 1s ticker cell
published both unconditionally — it never asked which slide they came from,
and `hm_result["params"]` recorded metric/tile/downsample/rows/cols but no
slide. So the defect came straight back, with a green success callout added on
top of it.

Nothing raises anywhere. The Navigator's `except Exception: pass  #
stale/mismatched grid` cannot fire, because a grid from another slide does not
raise — `render_heatmap` simply resizes it — and `grid_coverage` then rescales
slide A's 8x12 grid against slide B's dimensions into a registration that
means nothing. R04-3's own regression test (`tests/test_slide_change.py`,
2 passed) stays green throughout, because it pins the synchronous path only.

**Evidence** — app.py's REAL "Run heatmap" button on the 6000x4000 demo slide,
then app.py's REAL `open_slide_path` to a 600x400 slide, then app.py's own
ticker cell, against the pre-fix ticker:

```
E  AssertionError: slide A's metric grid was published while slide B is open.
   With 'show heatmap on navigator' ticked it is blended onto slide B's
   thumbnail and rescaled by grid_coverage into a registration that means
   nothing: {'metric': 'tissue_fraction', 'tile': 256, 'downsample': 1.0,
   'rows': 16, 'cols': 24}
```

Reachable in ordinary use: round 04 measured 9.15 s for a `nuclei_density`
sweep on the demo slide, and the TCGA slide in `data/tcga` is 81671x18211, so
changing slides mid-sweep is normal. Rated high rather than R04-3's medium

Deliberately NOT another clear at open time: that is exactly what the worker
thread walked around.

**Regression tests:** `tests/test_heatmap_provenance.py` (4) —

## R07-2 — the green "Analyzed …" callout reported a density inflated by the extraction downsample squared

**Severity:** high · **Status:** fixed

`detect_nuclei` derives its area from the mpp it is handed times the **patch's
own** pixel dimensions (`nuclei.py:136`: `area_mm2 = (h * mpp) * (w * mpp) /
1e6`). `extract_patch` reads from a downsampled pyramid level and then
thumbnails whatever is still wider than `max_size=1024`. app.py passed
`_src.mpp` — the LEVEL-0 value — so the area it divided by was too small by
the extraction downsample squared.

**Evidence** — app.py's OWN "Analyze current selection" cell, real
`analyze_button` click, against the pre-fix call site:

```
E  AssertionError: a 2048x2048 level-0 ROI was thumbnailed to [1024, 1024] px
   and the density was computed against the THUMBNAIL's area: reported
   6729.1/mm^2 where the ROI holds 1682.3/mm^2 -- overstated 4.00x, i.e. the
   extraction downsample squared. The callout above it is green and prints the
   true patch size [1024, 1024].
E  AssertionError: a 4096x4096 level-0 ROI ... overstated 16.00x ...
```

Exactly 4.00x and 16.00x — `(2048/1024)^2` and `(4096/1024)^2`. Any ROI up to
1024 level-0 px on its long axis is correct, which is why this survived: it
only appears as the user drags a bigger box. The verification pass measured
the same 16.00x on the real 81671x18211 TCGA slide (mpp 0.2526).

`AGENTS.md:215-216` gave the same two calls as its worked recipe
(`extract_patch(..., max_size=1024)` then `detect_nuclei(patch,
mpp=sel["mpp"])`, and `sel["mpp"]` IS `source.mpp`), so every agent following
the contract reproduced the error independently.

**Fix.** `hescope/rois.py` grows `patch_mpp(source, roi, patch)` next to
`extract_patch` — the same "derive the scale from bbox size / patch size"
rule `roi_shape_mask` already documents — and app.py's one call site uses it
for both `detect_nuclei` and `qc_report`. `AGENTS.md` 9's recipe now uses it
too, with a comment saying why `sel["mpp"]` is the wrong value there.

The fix is at the call site rather than inside `detect_nuclei` because
`detect_nuclei`'s contract (microns per pixel *of the image you hand it*) is
correct and is what every other caller relies on; what was missing was a way
for a caller to *know* the patch's mpp, which `extract_patch` discarded.

**Regression tests:** `tests/test_selection_density.py` (6) —
`::test_the_reported_density_matches_the_roi_it_names[800|2048|4096]` through
app.py's own cell, plus three unit tests pinning `patch_mpp` itself
(downsampled, not downsampled, and no-mpp slide) so a failure says which half
is wrong. The parametrized test asserts `count > 0` first: `detect_nuclei`
short-circuits to `_empty_stats()` whose density is None whatever mpp says,
and the test would otherwise pass on nothing.

Red with `_mpp = _src.mpp` restored: `2 failed, 4 passed in 7.72s` (the 800 px
case is genuinely unaffected, and its staying green is the point).

carrying every success string in the app: "Sent ROI to agent: …", "Saved
annotation for ROI N.", "Deleted ROI [i]", "Viewer centered on ROI [i].",

## R07-5 — a click that failed changed nothing on screen and said nothing

**Severity:** medium · **Status:** fixed (+ a lint rule)

marimo swallows an exception raised inside an `on_click` callback. Verified
directly:

```
$ python -c "import marimo as mo; b=mo.ui.button(label='Open', on_click=boom); b._update(1)"
on_click handler for button (button()) raised an Exception:
 Traceback (most recent call last):
  File ".../marimo/_plugins/ui/_impl/input.py", line 1285, in _convert_value
    return self._on_click(self._value)
  File "<string>", line 4, in boom
FileNotFoundError: [Errno 2] No such file or directory: 'E:\\slides\\biopsy_2026_03.svs'

NO EXCEPTION propagated to the caller; button.value = None
```

That traceback goes to the KERNEL's stderr — the terminal running `marimo
edit`, not the browser. `_on_open_clicked`, `_on_demo_clicked` and `_on_upload`
had no `try/except`, so a mistyped path or an unreadable upload produced *no
callout, no message and no state change*, with the previous slide still
rendered: byte-identical to successfully re-opening the same slide. A typo in
a path box is an everyday input.

The comment directly above that code says the panel is "Hardened: every widget
is constructed in its own try/except, so a failure renders a callout in place
of that widget" — the widget CONSTRUCTION is hardened, the ACTION was not,
which is exactly the gap that comment would lead a reader to believe is
closed.

**Fix.** The three handlers report through `set_db_msg`, which was already in
that cell's signature for the tile-server and registration failures. And,
because this class has now produced five findings across five rounds, a
**lint** rather than three patches:
`tests/test_message_channels.py::test_every_click_handler_has_an_error_path`
walks app.py's AST, collects every function passed by name to
`on_click=`/`on_change=` plus every `_on_*` function (which is how
`_on_browse_catalog` reaches `tcga_panel.make_filter_controls`), and requires
each to contain a `try`. Exemptions are a named list with a reason each;
today it holds one entry, `_on_clear_rois` ("two mo.state setters and nothing
else").

The lint immediately surfaced four handlers nobody had filed — `_on_add_roi`,
`_on_jump_bbox`, `_on_zoom`, `_on_zoom_fit`. **Stated plainly: those four were
found structurally, not reproduced.** They do geometry over live viewport
state rather than I/O, so no failing input was demonstrated for them; they are
guarded anyway, because a lint that has to exempt four genuine offenders is
worth nothing. The camera cell takes `set_db_msg` for this — referencing a
setter adds no dependency edge, only a getter would.

Known gap, stated rather than papered over: closures produced by a factory
(`on_click=_make_view(_i)`, the per-ROI View/Delete buttons) are not reachable
by name and are outside the rule. The test docstring says so.

**Regression tests:** `tests/test_message_channels.py` —
the lint above, `::test_the_handlers_we_expect_are_actually_being_checked`
(guard the guard: a rename that empties the handler set must not read as a
pass), and `::test_opening_a_path_that_does_not_exist_says_so`, which drives
app.py's real `path_input` and real "Open" button. Red with the try/except
removed:

```
E  AssertionError: an 'Open' that failed wrote nothing to the UI at all: no
   callout, no message, and the previous slide still rendered -- byte-identical
   to successfully re-opening the same slide
```

## R07-6 — a failed export was delivered as a successful download

**Severity:** medium · **Status:** fixed

`_export` and `_export_geojson` both ended in `except Exception as _exc:
return f"export failed: {_exc}"`, and that string went to
`mo.download(filename="rois.json", mimetype="application/json")`. The browser
performs an ordinary, successful download of a correctly named and correctly
typed data file whose body is an error message. Nothing is written to any
message channel.

**Evidence** — app.py's own annotation-editor cell with the database
unreachable, `mo.download` spied to capture the real callables:

```
  Export ROIs (JSON)            -> rois.json      (application/json)
      content: 'export failed: (sqlite3.OperationalError) unable to open database file'
      a consumer doing json.loads(rois.json) gets JSONDecodeError: Expecting
      value: line 1 column 1 (char 0)
  Export ROIs (CSV)             -> rois.csv       (text/csv)
  Export ROIs (GeoJSON, QuPath) -> rois.geojson   (application/geo+json)
  message channel (set_db_msg) after all three: UNSET
```

The user walks away believing the annotations are exported; the failure is
discovered later and elsewhere — QuPath rejecting `rois.geojson`, a script's
`json.loads` raising — with nothing pointing back at the click.

**Fix.** `mo.download` accepts a **callable filename**, evaluated at click
time (`marimo/_plugins/ui/_impl/input.py`, `_load` resolves the name and then
the data), so the name can report what happened: a successful export is still
`rois.json`, a failed one is `rois.json.EXPORT-FAILED.txt`. The export runs
once per click into a small `_pending` slot that whichever callable marimo
invokes first fills and the other consumes — order-independent by
construction, and it never serves a cached body to a later click.

`set_db_msg` was **not** used here on purpose: the data callable runs outside
the cell runner, where marimo does not resolve state updates, so a callout
written there would never render.

Honest limit: `mimetype` is fixed at construction, so a failed GeoJSON is
still typed `application/geo+json` while being named `.txt`. The filename is
what the user sees in their downloads folder, and it is unmistakable.

**Regression tests:** `tests/test_annotation_export.py` —
`::test_a_failed_export_is_not_delivered_as_the_data_file[json|csv|geojson]`,
`::test_a_successful_export_keeps_its_plain_filename`, and
`::test_each_click_re_reads_the_database` (guard against the per-click cache
serving stale bytes to the next click). Red with the plain filenames restored:

```
E  AssertionError: a failed export was delivered as rois.json -- right name,
   right mimetype, 'export failed: ...' as the body -- so the browser performs
   an ordinary successful download and the failure only surfaces later, in
   whatever tried to read the file
```

## R07-7 — the GeoJSON button downloaded nothing while its neighbours downloaded everything

**Severity:** medium · **Status:** fixed

app.py's own comment above the three Export buttons states the contract for
all three: *"Export the current slide's ROIs (or all when no slide is open)"*.
`export_rois(engine, slide_id=None)` honours it (the WHERE clause is skipped).
`slide_geojson_text(engine, None)` returned an empty FeatureCollection by
design — *"so the button is always safe to click"* — and app.py never
reconciled the two.

`get_slide_id()` is None whenever no slide has been opened yet, and also
whenever `db.slide_repo.register` raised during an open.

**Evidence** — app.py's own cell, `get_slide_id() -> None`, a real SQLite

```
  Export ROIs (JSON)            -> rois.json       983 bytes
  Export ROIs (CSV)             -> rois.csv        537 bytes
  Export ROIs (GeoJSON, QuPath) -> rois.geojson     51 bytes

shows nothing, which reads as "this slide has no annotations" rather than "the

**Fix.** `slide_feature_collection(engine, None)` now means EVERY saved ROI,
matching `export_rois`. `mpp` is a per-slide constant and those rows span
slides, so it rides on each row — `rois_to_geojson` already lets a row-level
`mpp` win over the argument.

**Regression tests:**
`tests/test_annotation_export.py::test_with_no_slide_open_all_three_exports_agree`

`tests/test_geojson.py::test_slide_geojson_text_with_no_slide_open_exports_every_roi`.
The pre-existing `::test_slide_geojson_text_with_no_slide_open_is_an_empty_collection`

and new contracts are indistinguishable, which is exactly why it never caught
this.

Red with the empty FeatureCollection restored: `2 failed`, including

```
E  AssertionError: the GeoJSON button downloaded an empty FeatureCollection

   QuPath opens an empty collection happily and shows nothing, which reads as

## R07-8 — a successful train reset both heatmap dropdowns, and the obvious guard is a false green

**Severity:** medium · **Status:** fixed

`set_models_version(object())` fires on the train-success path. That re-runs

model written non-atomically is strictly better than a training run lost to a

## R07-12 — `ensure_server()` leaked the port of the server it replaced

**Severity:** low · **Status:** fixed

`ensure_server` did `if isinstance(srv, TileServer) and srv.is_alive(): return
srv`, else constructed a new one and overwrote the `sys` attribute — it never
called `shutdown()`/`server_close()` on the one it dropped. `is_alive()` is
False as soon as the listener THREAD dies, which an exception escaping
`serve_forever` does *without* running `shutdown()`, and the socket stays
bound. The module's own docstring names this as the invariant the singleton
exists to protect: it lives on `sys` precisely so a reload does not "leak the
previous server *and its port*, one per reload".

Second half: `shutdown()` was idempotent but not terminal. A shut-down server
still accepted `register()` and handed back a well-formed `tile_source` dict
on a dead port. app.py's `except Exception -> falling back to the legacy
plotly viewer` guard cannot fire on a success, so the user got a permanently
blank OpenSeadragon canvas and no message.

**Evidence** — the listener killed without `shutdown()`, then `ensure_server()`
again, against the pre-fix code:

```
E  AssertionError: the replaced server's socket is still bound; its port is
   leaked for the lifetime of the process, one per recovery
E  assert 2756 == -1
E  Failed: DID NOT RAISE RuntimeError
```

**Fix.** `ensure_server` shuts the dead server down before replacing it, and
`register` raises on a shut-down server so app.py's fallback becomes
reachable.

**Regression tests:**
`tests/test_tileserver.py::test_ensure_server_shuts_down_the_dead_server_it_replaces`,
`::test_a_shut_down_server_refuses_to_register` (which also re-asserts that
`shutdown()` is still idempotent).

## Observations (not bugs)

- **REFUTED — the highest-severity claim in the whole set.** *R07-B2* held
  that the Navigator's `get_thumbnail()` racing the tile server's threads on
  one `TifffileSource` corrupts 6% of navigator thumbnails and 404s 550 tiles.
  The verification pass built the three-arm experiment twice from scratch —
  synthetic JPEG-compressed pyramidal SVS, then the real 81671x18211 TCGA

- **The mechanism that makes it safe, which SUMMARY item 6 should record.**
  `tifffile` flips `TiffFile.filehandle.lock` from `NullContext` to a real
  `RLock` the moment `aszarr` opens a zarr store, and both `series.asarray()`

  thread** before returning the key, so the lock is armed before any tile
  thread or Navigator render runs. SUMMARY open item 6 is right in outcome;
  the precise wording should be that the pre-warm is not warming a cache, it
  is arming tifffile's own file-handle lock, and a future backend that never
  builds a zarr store would not get it. (tifffile 2026.3.3, Windows 11,
  CPython 3.11.)
- **A switch that disables the only lock the tile path has.**

  `entry.read_lock` from the tile path entirely. Off by default and untested
  enabled, so an observation rather than a finding — but it deserves a line in
  the record so a future round does not measure with it set and blame the
  wrong thing.

- **`os.replace` is not a complete answer on Windows.** Recorded under R07-10:

  silent vanishing. Any future "write it atomically" fix in this repo needs

- **The review process was writing into the artefact it audits.**
