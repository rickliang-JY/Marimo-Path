## R03-1 — `OpenSlideSource.read_region` pads off-slide pixels with black

**Severity:** high · **Status:** fixed

`hescope/slides.py:169` built its crop box as

```python
crop = img.crop((sx0 - lx, sy0 - ly, sx1 - lx + (sx1 - sx0), sy1 - ly + (sy1 - sy0)))
```

The `+ (sx1 - sx0)` / `+ (sy1 - sy0)` terms double the box. openslide returns
RGBA with everything past the slide edge **transparent**, which
`.convert("RGB")` turns into **black**, so the doubled crop pastes that black
straight over the white padding the method's own docstring promises ("Clipped
to slide bounds and padded with white"). `PillowSource` and `TifffileSource`,
which document the identical contract, both pad with white.

`open_slide()` prefers `OpenSlideSource` for every `.svs`, so this is the
default backend for real WSIs.

Black is not inert: `roi_stats` and `grid.tissue_fraction_proxy` both classify
a pixel as tissue when `luminance < 0.9 * 255`, and black passes that test with
room to spare.

## R03-2 — annotation-browser click-to-jump raises on every row

**Severity:** medium · **Status:** fixed

`app.py:1698` renders the table cell as `"bbox": str(_r["bbox"])`, and
`app.py:1682` reads that same value back out of the selected row and hands it
to `jump_viewport_for_bbox`, which does `x0, y0, x1, y1 = (float(v) for v in
bbox)`. Iterating a string yields characters.

**Evidence** (`scratchpad/probe_jump.py`, driving the real `bootstrap_db` /
`ROIRepo` and reproducing the two app.py lines verbatim):

```
db.enabled: True
row['bbox'] from ROIRepo.for_slide : [1000, 2000, 1600, 2600] list
row['bbox'] as put into mo.ui.table: '[1000, 2000, 1600, 2600]' str
annotation-browser jump -> RAISED ValueError: could not convert string to float: '['
sidebar 'View' button   -> ((1300.0, 2300.0), 1.171875)
```

The sidebar "View" button, which passes `roi.bbox()` (a tuple), is the control
group: same helper, same slide, works.

> **Evidence correction.** The `1.171875` above came from a 640x640 viewport,
> not app.py's own. With the notebook's default `ViewportState(..., size=(1024,
> 768))` (`app.py:243`) that same 600x600 bbox clamps to `downsample=1.0`, and
> both the fixed handler and the control return `((1300.0, 2300.0), 1.0)` —
> which is what `tests/test_annotation_jump.py` now asserts. The ValueError,
> i.e. the finding itself, reproduces verbatim either way.

The handler has no `try`/`except`, so the ValueError propagates out of
`mo.ui.table`'s `on_change` — the table's own label says "select a row to jump
the viewer".

**Fix.** Carry the numeric bbox in a `{id: bbox}` map built from `db_roi_rows`
and look it up by the row's `id`; the table keeps its readable string column.
The map is passed into the handler **as a function parameter** via a
`_make_row_jump(bbox_by_id)` factory rather than referenced from the handler
body, because a cell-private name is mangled and discarded when the cell ends
and the handler would die at click time — the same shape the ROI panel's
`_make_view(_idx)` already uses.

**Regression test:** `tests/test_annotation_jump.py::test_annotation_row_click_moves_the_openseadragon_camera`
and `::test_annotation_table_still_shows_the_bbox_as_text`.

This round originally recorded "test coverage: none" for the reason under R01-4
— marimo cell code, and a test that re-implements the row composition tests the
copy. That reasoning was right about re-implementing and wrong about
impossible. The test **executes app.py's own source text**: `ast` finds the
`@app.cell` function containing the annotation browser (and, separately,
`move_camera` and the camera-consumer cell), the segments are compiled with

## R03-3 — the same handler moved only the legacy surface

**Severity:** low · **Status:** fixed

> **Severity correction (verification pass): medium → low.** The claim that
> this is "independent of R03-2" does not survive being tested. On the pre-fix
> tree the line was never reached: `jump_viewport_for_bbox` raises on the
> string bbox before it returns, and a stringified bbox is never 4 characters
> long, so `set_vp(dc_replace(...))` was dead code with no input that reaches
> it. No observable pre-fix behaviour is attributable to R03-3 alone. It is a
> genuine defect, and it would have become a live *silent* bug the moment
> R03-2 was repaired on its own — which is exactly "latent; needs an uncommon
> configuration or input to trigger" on this log's scale. Worth fixing in the
> same change; not worth medium.

Masked by R03-2. The handler ended with

```python
set_vp(dc_replace(get_vp(), center=_center, downsample=_ds))
```

`set_vp` updates `ViewportState` only — navigator, header readout, the agent
contract's `viewport_downsample`. The command that actually moves the
OpenSeadragon widget is `set_cam`, and the one helper that does both is
`move_camera` (app.py:269, "commands the OpenSeadragon widget ... so the two
surfaces never disagree"). The consumer cell at app.py:1290 even lists
"annotation click-to-jump" among the things that reach the widget through it —
but nothing on that path ever called `set_cam`.

So with the bbox repaired, clicking an annotation would still have left the
default viewing surface exactly where it was while the navigator rectangle
jumped somewhere else. This is the same class as the three dead toolbar
buttons: a second place re-deriving what `live_selection()` / `move_camera`
already own.

**Fix.** Call `move_camera(...)`, as the ROI panel's "View" button does. The
cell's `set_vp` parameter is replaced by `move_camera`.

**Regression test:** the same
`tests/test_annotation_jump.py::test_annotation_row_click_moves_the_openseadragon_camera`,
whose last assertion is about the widget and not about `ViewportState`: after
the click it runs app.py's own camera-consumer cell (the `_cmd = get_cam()`
one) against a recording stub and requires a `goto`.

Because R03-3 is latent behind R03-2, a stash of the whole file only proves the
ValueError. It was pinned separately by re-introducing R03-3 **alone** — the
bbox fix kept, `move_camera` swapped back to `set_vp` in the cell's signature
and body:

## R03-4 — the metric grid spans more than the slide, but is drawn as if it fit

**Severity:** low · **Status:** fixed

`grid_shape` rounds the cell count up, so a grid of `rows x cols` covers
`cols * tile * downsample` by `rows * tile * downsample` level-0 pixels — up to
one whole cell more than the slide. `render_heatmap` resized the grid to the
base image's size, i.e. assumed the two extents are equal, so every cell was
drawn slightly too large and the error accumulated toward the bottom-right.

**Evidence** — the app's own heatmap parameters on the real slide:

Re-measured in the verification pass by rendering a grid whose only valid row
is the bottom one over a black base and finding the first overlaid thumbnail
row (`scratchpad/probe_r03_4.py`):

```
tile=256 downsample=6.6464 cell=1701.48 grid=11x48
grid covers   81671.0 x 18716.3 level-0 px
slide is      81671 x 18211 level-0 px
grid_coverage -> fx=1.000000 fy=1.027745
thumbnail 512x114
bottom grid row starts at thumbnail y = 104 (coverage=None, old behaviour)
bottom grid row starts at thumbnail y = 106 (coverage=grid_coverage(...))
TRUTH: the bottom row's tissue starts at level-0 y=17014.8 = thumbnail y 106.51
stretched (old) boundary in level-0 px: 16555.5
worst INTERIOR boundary displacement  : 459.3 level-0 px
total grid overhang past the slide    : 505.3 level-0 px
mpp=0.2526  -> 116 um
coverage=None is byte-identical to coverage=(1.0, 1.0): True
horizontal: cols*cell = 81671.0  W = 81671  fx = 1.0
```

> **Evidence correction.** The line originally recorded here,
> `worst displacement: x 0 px, y 505 level-0 px`, mislabels a number: 505.3 is
> the grid's total overhang past the slide (18716.3 − 18211), not a boundary
> displacement. The largest displacement at an interior boundary is
> `gy * (cell − H/rows) = 10 * (1701.48 − 1655.5) = 459.3` level-0 px — the
> figure the same evidence block quotes two paragraphs later, and the one
> measured above.

Low because the error is bounded by one cell out of `rows` (~2.8% here, ~116 µm
at this slide's 0.2526 mpp) and the heatmap is a navigation aid, not a
measurement. On this slide only the vertical axis is affected — 48 columns x
1701.48 = 81671.04 against W = 81671, so `fx` is 1.0 to seven digits. It is
still a silent misregistration between a metric and the tissue it was measured
on, which is exactly the failure mode this lens exists for.

**Fix.** New `heatmap.grid_coverage(slide_dimensions, grid_shape, tile=,
downsample=) -> (fx, fy)` and a `coverage=` keyword on `render_heatmap`: the
grid is scaled to the extent it really covers and then cropped back to the base
image. `coverage=None` keeps the old behaviour byte-for-byte, so no existing
caller changes. Both app.py call sites (the heatmap panel and the navigator
blend) now pass it.

**Regression tests:** `tests/test_heatmap.py::test_render_heatmap_coverage_keeps_cells_on_their_own_pixels`
(a 2-row grid over a base 1.5 rows tall: the row boundary must land at y=32,
and the test also pins where the unfixed stretch put it, y=24),
`::test_grid_coverage_is_one_when_the_slide_divides_evenly`,
`::test_grid_coverage_matches_the_real_sweep`,
`::test_render_heatmap_coverage_defaults_to_the_old_behaviour`.

Stashing `hescope/heatmap.py` wholesale cannot demonstrate these — `hescope/__init__.py`
imports `grid_coverage`, so the module will not even load. Instead only the
`render_heatmap` resize block was reverted to its pre-fix two lines, keeping

## Observations (not bugs)

- **The overview tier's downsample is single-axis.** `_build_overview` sets
  `overview_downsample = layout.width / thumb.width` and `render_tile` uses it
  for both axes. Measured aspect error on the real slide: -0.074% (OpenSlide,
  2048x457) and +0.145% (tifffile, 1024x228) — under half a pixel of the
  overview, and the overview tier only serves the coarsest zooms. Not worth a
  second field.
- **Nothing clamps a selection to the slide.** `parse_osd_selection` and
  `ROI.bbox()` clip at 0 but not at `slide_dimensions`, so `bbox_level0` in the
  agent contract can exceed the slide. That is arguably correct (the user did
  draw there, and `read_region` pads), but it is what made R03-1 reachable, and
  it means `width_px` in `roi_stats` can describe a patch that is partly void.
- **`records_to_rows`-style stringification appears once more**: the ROI panel
  and the annotation browser both render coordinates as text, but only the
  annotation browser reads them back. Worth a look if a third table is added.
- **Marimo cell code is testable after all, if the test runs the real source.**
  R01-4 and the first draft of R03-2 both recorded "test coverage: none"
  because a test that re-implements a cell tests the copy. That is true, but it
  rules out the wrong technique, not the goal:
  `tests/test_annotation_jump.py` slices the `@app.cell` function out of app.py
  with `ast`, compiles the segment with its real line numbers and calls it with
  stub dependencies. Nothing is re-implemented and the failure points at the
  real app.py line. Two limits are worth knowing before reaching for it again:
  the cell's dependencies have to be stubbable (this one takes ten, all
  callables and plain data), and exec does **not** apply cell-private name
  mangling, so it cannot replace the source guard in
  `tests/test_toolbar_actions.py`. R01-4's TCGA status message is the obvious
  next candidate.

## Checked and found clean

- **`viewport_from_osd` <-> `osd_bounds_from_viewport`** round-trip over 20,000
  random states (slide sizes to 200k px, container 64..3000, bounds spanning
  1e-4..4 viewport units, negative origins): worst relative error
  **1.4e-11**. Both axes are normalized by W0 in both directions.
- **`viewport_from_osd` against hand-computed expectations**: container centre
  maps to `vp.center`, `(0,0)` maps to `(bx*W0, by*W0)`, `(cw,ch)` maps to
  `((bx+bw)*W0, (by+bh)*W0)`.
- **`rois.viewport_transform`** round-trip over 20,000 random viewports: worst
  absolute error **3.5e-10 px**.
- **DZI core tiles tile each level exactly** — summed core areas equal
  `level_size` for every level of 81671x18211, 1000x1000, 1x1, 65536x100 and
  513x4097 (no gaps, no double coverage).
- **`_source_edge`'s seam rule holds at fractional ratios** — with the real
  `level_downsamples` `(1.0, 4.0004, 16.002, 32.004)`, neighbouring tiles'
  core edges resolve to the identical source pixel at every sampled level; 0
  mismatches.
- **A served tile shows the level-0 pixels it claims to.** Fetched over HTTP
  from a live `TileServer` and compared against an independent
  `read_region` + resize of the same `level0_box`: mean |diff| 1.37 (interior,
  full res), 0.16 (interior, 2 levels up), 3.44 / 1.57 at the right and bottom
