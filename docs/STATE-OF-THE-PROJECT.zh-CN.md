## 4. 存储层

### 4.1 WAL —— 优先级最高，因为它现在就在出故障

**现象。** 两个进程同时碰数据库时，写入失败。

**证据。** `PRAGMA journal_mode` = `delete`（默认）。实测：当另一个连接持有读时，一次
ROI 保存**在 5.5 秒后以 "database is locked" 失败**；同样的写入在 WAL 下是 0.00 秒。

**为什么现在就重要。** 触发条件不是罕见情况，而是这个项目的核心工作流：app 开着，
agent 通过 marimo-pair 读同一个库。再加上 `hescope` CLI、第二个 marimo 会话、或我这一天里
跑的任意一次只读探针。

**可选方案。**
- (a) 开 WAL + `busy_timeout`。
- (b) 只加 `busy_timeout`（重试而不改日志模式）——能减少失败，但读写仍互斥。
- (c) 不动，靠"别同时开两个"的口头约定。

**建议：(a)，而且第一个做。** 在 `get_engine` 里与已有的 `foreign_keys=ON` 并排设
`journal_mode=WAL` 和 `busy_timeout`，加一个测试同时断言这三个 pragma。改动一行，风险是
WAL 在某些网络文件系统上不可用——所以要 `try/except` 降级并把降级**说出来**，不要静默。

### 4.2 身份 —— `(scheme, key)`，不是内容哈希

**现象。** 一张片子是谁，由它此刻在哪个路径决定。

**证据。** `demo_he.png` 同时是 slide 3（挂着 2 个 ROI）和 slide 31（0 个）；31 行里 18 行
指向已不存在的文件；上传走 `mkdtemp()` 所以同一文件传两次是两张片子；
`normalize_slide_path` 在 Windows 上把同事的 `/mnt/nfs/slides/A1.svs` 变成
`E:\mnt\nfs\slides\A1.svs`；`SlideRepo.register` 是 check-then-act，**8 个并发注册同一张片子
有 3 个抛 `IntegrityError`**。

**可选方案。**
- (a) 内容哈希做主键（我在 `DATABASE-DESIGN.md` 里的原方案）。实测 `size + 首尾 1MiB`
  的 sha256 是 0.002 秒，比全量快 84 倍。**但 `NOT NULL` 会堵死整个"用户自有数据库"场景**
  ——DICOMweb series 没有文件也没有大小。
- (b) `(scheme, key)` 复合身份：`('sha256', <hash>)` 给本地文件，
  `('dicomweb', '<study>/<series>')`、`('omero', '<id>')`、`('path', <normalised>)` 兜底。
  `UNIQUE(scheme, key)`。
- (c) 让用户手动指定 slide id。

**建议：(b)。** 它把 (a) 保留为本地文件的默认，同时不把"必须是个文件"写死进 schema。
配套三件事：`slide_files` 表承载"一张片子的多个路径"（现有 18 条死路径就变成
`missing_since` 标记而不是 18 张幽灵片子）；`register` 改成 `INSERT ... ON CONFLICT` 消除竞态；
`normalize_slide_path` 对非本机路径不再套用本地盘符规则。

### 4.3 迁移 —— 已经毁过一次数据

**现象。** 没有版本标记、没有 runner，而唯一存在的那次迁移丢了来源信息。

**证据。** `PRAGMA user_version` = 0。`hescope migrate-tcga-catalog` 把 50 行的
`first_seen_at` 从源值重置为迁移时刻——**丢了 25 小时**——因为 `cli.py:312-327` 构造行时
没带这个键，列落到了 `default=_utcnow`。它的 5 个测试断言的是计数
（`stats()["files"] == 3`），**从不拿源列比目标列**。

更隐蔽的一条：`init_db` 的隐式升级（`create_all` + `PRAGMA table_info` +
`ALTER TABLE ADD COLUMN`，`db.py:98-129`）产出的 schema 与全新 `create_all` **实质不同**
——升级过的 `rois` 有 0 个索引，全新的有 2 个；`server_default` 被静默丢弃。而两者都报
`user_version = 0`。

**可选方案。**
- (a) 引入 alembic。
- (b) 自建：`schema_migrations` 表 + 一组按版本号排列的函数，forward-only。
- (c) 继续现状。

**建议：(b)。** alembic 会带来依赖和一套与本项目习惯不同的工作流；这个 schema 的变更
频率不高，自建三十行足够。硬性配套：**每个迁移必须有一个测试，读源里的一个值、断言它
出现在目标里**——计数不是证据，那次丢数据的迁移正是被计数测试放过的。另外先把当前 schema
盖章为 version 1，并修掉 `init_db` 的加列不加索引。

### 4.4 时间戳 —— 一个静默的 8 小时错误

**现象。** 四套约定并存，其中两套写进同一个文件。

**证据。** `db.py:35` naive UTC、`tcga_schema.py:57` **aware** UTC、`ml.py:69` aware ISO 串、
`agent_bridge.py:146` 无偏移量的文件名格式。而 SQLAlchemy 的 SQLite `DATETIME`
**会静默丢弃偏移量**：存 `12:00+08:00` 落盘成 `'2026-01-01 12:00:00.000000'`，`db._iso` 再把它
当作 `+00:00` 读回来。**8 小时误差，全程无异常。** 今天恰好都对，只因为所有写入方都在 UTC。

**建议。** 落盘一律 naive UTC，读边界转换（`db._iso` 已经这么做）。加一个测试：向
`DATETIME` 列传 aware datetime 直接失败。

### 4.5 不变量交给数据库

补上两个缺失的外键；加上能拦住库里已存在的重复 ROI 的唯一约束；把裸 sqlite3 写入路径
统一到 `get_engine`（或至少让它们设同样的 pragma）。

## 5. 接口层

### 5.1 返回契约现在是四套

**证据。** `update_annotation`/`delete` → `bool`；`add`/`register`/`record` → `int`；
`InteractionRepo.record` → `int | None` 且永不抛；`SlideRepo.delete` → `None`；
`SlideCatalog.mark_downloaded` → `None`；`import_annotations` → `list[int]`。没有规则在它们
之间做选择。

后果是具体的：**两个同名的 `mark_downloaded` 行为相反**——`SlideCatalog` 的对未知 id 静默
no-op，`TcgaCatalog` 的**凭空造出一行没有元数据的记录，而且这行从此计入"已下载"**
（`tcga_schema.py:370-379`）。两者都返回 `None`，调用方无从分辨。

**建议。** 一条规则：**写操作返回它做了什么**——新建返回 id，修改已有行返回 `bool`，
永不返回 `None`。不会失败的方法在名字或 docstring 里说明；其余一律抛。agent 侧的包装层
永不抛（那是 `AGENTS.md` 的契约），因此它必须**转换**异常，而不是吞掉。

### 5.2 agent 唯一的写入路径把自己的结果丢了

**证据。** `agent_bridge.py:275` 调 `roi_repo.update_annotation(rid, ...)` 却**丢弃了返回的
`bool`**——那个 bool 正是 round 07 为"分辨 no-op 与真写入"加的。实测后果：当行在存在性检查
和写入之间被删掉时，`annotate_roi` 返回了裸 JSON 字符串 `'null'`（第四种、任何文档都没写的
返回形状），并且**仍然写了一条 `label_set` 的 interactions 记录**，声称标签设置成功。

**建议。** 消费那个 bool；返回形状收敛到文档写明的两种；写入失败时不写 interactions。

### 5.3 分页在 Python 里做

**证据。** `query_annotations(limit=50)` 取回**全部**行再切片：5000 个 ROI 时 17.4 ms，而
SQL `LIMIT 50` 是 0.7 ms，且到 20000 仍然平坦。`ROIRepo.for_slide` 根本没有上限——5000 个
ROI 时 138 ms + 170 KB，**每次 overlay 重渲染都全额支付**。

**建议。** 所有列表方法接 `limit`/`offset` 并下推到 SQL；视口查询接 bbox（需要 §4.2 之后的
四个 `REAL` bbox 列——现在 `bbox_json` 是文本，这个查询根本写不出来）；没有方法返回无界结果集。

### 5.4 一个版本化的公共 API

repo 是内部实现。实验室要写自己的工具（§6）就需要一个不会变的表面：`hescope.api`，
显式版本号，包装 repo，返回普通 dict，并有测试在形状改变时失败。

## 6. 用户自有数据库

这是你提得最准的一点：**不能默认用户从 TCGA 下数据、且没有自己的库。**

### 6.1 我们文档里的承诺被夸大了

| 文档说 | 实测 |
| --- | --- |
| 「换 PostgreSQL 只是一个环境变量」（`README.md:230`） | **驱动一个都没装**（psycopg2 / psycopg / pymysql / asyncpg 全无），`pyproject.toml` 里没有 db extra，另有三处 SQLite 专有假设未处理 |
| DICOMweb 需要新依赖 | **`dicomweb-client` 0.61.1 已经装了**（`wsidicom` 的硬依赖），`WsiDicom.open_web` 现成。读 PACS **0 新增包** |

### 6.2 五种真实形态与代价

按实测代价排序：

1. **DICOMweb / PACS 读取** —— 0 新增包。最便宜的一步，而且 PACS 是权威源，和一个文件夹
   不是一个性质。
2. **一堆 SVS + 一个标签 CSV** —— 除了列映射之外不需要新代码。这可能是最常见的形态。
3. **QuPath 工程目录** —— `hescope/importers.py` 已经能解析它的 GeoJSON，缺的是"遍历一个
   工程"而不是"解析一个文件"。
4. **实验室 Postgres** —— 一个驱动，加上修掉三处 SQLite 假设。
5. **OMERO** —— 真正的新依赖，提案前先量。

### 6.3 立场

**适配导入 + 导出 + DICOMweb 实时读**，不做全联邦。

理由：联邦意味着每次查询都要跨一个我们不控制的网络，并且让 ROI 与测量的溯源链依赖对方的
可用性。导入给我们一个可推理的存储；DICOMweb 单独给实时读，因为它免费、而且 PACS 是权威的。

**双向流动的硬要求：** ROI 从我们这里出去、从他们那里进来，都**不能丢失 provenance 和
测量时的分辨率**。这直接依赖 §7 的结论——一个不带成立条件的测量值，导出到别人系统里就
是一个无法证伪的数字。

## 7. 分析的可信度 —— 全文最重要的一节

### 7.1 同一块组织，密度差 29.4 倍

这是我亲手复现的，用的是你自己画的那个 ROI（`bbox = [61107, 8015, 65042, 11310]`），
`patch_mpp` 每一步都算对、都传对：

| `max_size` | patch | 有效 mpp | 核数 | density/mm² |
| --- | --- | --- | --- | --- |
| 256 | 256×214 | 3.889 | 167 | 201.5 |
| 512 | 512×429 | 1.941 | 595 | 718.7 |
| 1024 | 1024×857 | 0.971 | 1 916 | 2 314.7 |
| 2048 | 2048×1715 | 0.485 | 4 904 | **5 927.3** |

**29.4 倍。** 一个随提取上限变化 29 倍的「每平方毫米核密度」不是组织的属性，是栅格的
属性——只是穿了个物理单位的外衣。

同一现象的另外两个实测：`blur_score` 随同一个上限变化 6.72 倍；**两个都叫
`tissue_fraction` 的函数在同一块 patch 上相差 2378 倍**。

**这推翻了我之前两份文档的共同前提。** 我写过「记下 `mpp_effective` 就能让 R07-2 的坑变得
可表达，用 `WHERE` 排除不可比的行」。记录分辨率让你能**察觉**不可比——它**不能让那个数字
变得有意义**。

**可选方案。**
- (a) 只记录 mpp，比较时用 WHERE 过滤（原方案）。
- (b) 把所有测量固定在一个分辨率上做。
- (c) 每个 skill 声明一个**实测的有效分辨率区间**，区间外**拒绝执行**并记录 `rejected`。

**建议：(c)，并把 (b) 作为默认路径。** (a) 不够，因为它把判断留给了读数据的人，而自主
运行时没有这个人。(b) 单独用会让大 ROI 要么慢到不可用、要么被迫降采样——所以是：默认在
声明的区间内选择提取参数，做不到就拒绝，而不是降采样后照常输出。

### 7.2 QC 覆盖不了自主运行需要的东西

**证据。** `qc_report` 能检出明显失焦（σ≥2），别的基本没有。一张灰度的、非 H&E 的
patch 能通过它（`is_blurry=False`），而 `roi_stats` 在同一张图上会给出一个自信的 H&E
反卷积结果。**无人值守时，这就是在一张没有苏木素的图上测苏木素。**

**建议。** 在 skill 契约里加一条「输入前提」，由 QC 判定；QC 至少要能回答"这是不是一张
H&E 图"和"染色是否在参考范围内"（后者的参考矩阵 §3.2 说了，已经有了）。

### 7.3 扫描是有偏的，不只是被截断

**证据。** `iter_grid` 的 `max_tiles=4000` 上限打断了 row-major 顺序
（`hescope/grid.py:92-98`），所以被截断的扫描**系统性地偏向切片顶部**，未扫描的部分不是
随机的。

**后果。** 自主 loop 若从被截断的扫描里采样，会静默继承这个偏置——而且它会表现为"这张
片子的上半部分更有信号"，一个听起来完全合理的结论。

**建议。** 截断必须按空间均匀采样（或至少 stride 采样），并且**把截断这件事写进结果**
——现在扫描结果连网格都不落盘（§R1），更不会记录它只覆盖了多少。

## 8. 自主运行与 skill

### 8.1 skill 契约

一个能被无人值守调用的 skill，必须声明：

- **输入与单位**，以及它假设的染色/模态；
- **实测的有效分辨率区间**（§7.1），越界拒绝；
- **确定性与幂等性**：同样的输入是否给同样的输出，重复执行是否安全；
- **运行上界**：超时怎么办；
- **它写什么**：哪些表、哪些行；
- **它必须产出什么证据**才能让结果被相信。

### 8.2 报告

生成的报告是整个系统里风险最高的产物——它是人真正会读、并据以行动的东西。

**硬要求：报告里的每一个数字都携带四样东西**——它来自哪个 ROI、由哪个方法的哪个版本
产生、有效 mpp 是多少、以及所在 patch 的 QC 判定。**凑不齐这四样的数字不允许出现在报告里。**
另外，**实测的结论**与**推断的结论**必须分开排版，推断结论要点名它依赖的实测结论。

### 8.3 human gate

`human_gate` 是 `interactions` 里一个保留的 kind，**没有 UI、也没有任何代码写入它**。
它应该在这些时刻拦住 loop：

- skill 因分辨率越界被拒（§7.1）；
- QC 判定低于阈值；
- agent 提出的标签与人在重叠 ROI 上给的标签冲突；
- 对任何**人还没打开过的片子**的第一次写入。

### 8.4 LoopX 的位置

`E:\Good Github Repo\Agent\loopx` 是一个**状态内核 / 本地优先的控制平面**，不是 agent
框架。实测代价：**1 个包、0 卸载、`dependencies = []`**——本次会话量过的所有集成里最便宜的
（对比 wsidicom 7/0 采纳、tiatoolbox 152/22 拒绝）。它内置的 `ml_experiment` domain pack
自带 hypothesis ledger（`active → supported | weakened | retired`）、dataset window、
baseline-vs-candidate 比较，以及一个 **`guardrail_status`** 槽位——那正是 §7.1 的检查该待的
地方。

**但它的位置往后挪了。** 采纳 LoopX 仍然是对的，理由也仍然成立；只是**在数字还会跳 29 倍
的时候上治理，产出的是"可审计的胡说"**。先做 §7，再上 LoopX。

一条会落到我们 schema 上的约束：那个 pack 在代码里拒绝绝对路径、盘符和 URL 进入 ledger
字段，而我们的片子身份现在就是一个绝对 Windows 路径——这又是 §4.2 的一个论据。

## 9. 前端

### 9.1 ROI 编辑的地基已经在了，只是没接

**证据。** 画布已经发出 ROI 点击事件：`clicked_roi` 在 `hescope/osdviewer.py` 里出现 5 次、
在它的测试里 9 次、**在 `app.py` 里 0 次**。

**这改变了问题的性质**：不是"ROI 编辑不存在，要从头做",而是"选中这个原语已经实现并测试
过了，差一个消费方"。移动、拖顶点、画布上删除，全都建立在选中之上。

**配套的数据决定**（这部分不能省）：几何一旦改变，挂在这个 ROI 上的测量必须**删除**
——静默保留是这个项目最熟悉的那类缺陷。而且 `rois.patch_path` 不是测量，它是**训练输入**
（`ml.py:252-263` 每次训练都读这个 PNG），所以改几何还必须让 patch 失效。

### 9.2 agent 在界面里没有存在感

如果 agent 在自主分析（§8），用户**看不到它在做什么、发现了什么，也没法叫停**。

这是前面几节共同制造出的最大 UI 缺口，而且它**不需要任何 schema 改动**——机制已经有了：
`interactions` 表已经记录了每一次 agent 工具调用，带 actor。

**建议。** 一条常驻的 agent 状态条：正在跑什么、在哪个 ROI 上、跑了多久、上一个结论是
什么、以及一个停止按钮。数据来自 `interactions` + `skill_runs`，不引入新状态。

### 9.3 信息架构

侧栏（Open slide / Display / Navigator / ROIs）+ 中间的 viewer 与状态栏 + **五个默认全部
折叠的手风琴**（Annotations / Statistics / Analysis / Agent console / TCGA browser）。

现状可用，但对一个病理医生的实际工作流，"所有分析能力都在折叠的抽屉里"值得重新考虑。
这一条我给的是**观察**而不是建议——它需要你（真正的使用者）判断，我没有立场替你定。

另外一条实测的小问题：**"Zoom to fit" 并没有 fit**——它框住的是 81 671 px 里的 54 471 px，
而工具栏滑块够不到能真正 fit 的那个 downsample。

### 9.4 性能

**缩放。** 一次缩放约 28 个 tile。实测：

| `HESCOPE_TILE_PARALLEL_READ` | 顺序 | 8 线程 | 加速比 |
| --- | --- | --- | --- |
| 未设（默认） | 2163 ms | 2168 ms | **1.00x** |
| `=1` | 2210 ms | **425 ms** | **5.20x** |

**2.16 秒 → 0.43 秒**，而且并行取回的字节与顺序取回逐位相同。这个开关已经在代码里。

我**没有**改默认值，并且把还没证明的部分点名了：只测了一个进程、一张片子、一个后端
（tifffile/zarr，OpenSlide 路径未测）、单次而非分布、没测持续负载下的内存。**下一步是
基准工具，不是改默认。**

根因还有一条：DZI 有 18 层而文件只有 4 层（downsample 1/4/16/32），中间 14 层是实时合成
的，最贵的正是夹在文件层级之间的（level 15 冷 84 ms）。合成层可以磁盘缓存,它们是确定性的。

**ROI 加载。** 100 / 1000 / 5000 个 ROI 分别是 3.6 / 48.8 / 138.4 ms，每次重渲染全额支付。
今天只有 10 个所以无感，导入一个 QuPath 工程就是 10³–10⁴。修法不是加缓存，是 §5.3 的
视口查询。
