## 1. 存储层 ●

**做到了什么**

- 三层迁移框架：`schema_migrations` + forward-only runner + 可信的 `--dry-run`（实测在真库副本上零写入，副本与原文件逐位相同）
- 片子身份从"文件路径"改成 `(scheme, key)`，内容哈希实测 0.002 秒（比全量快 84 倍），且不把"必须是本地文件"写死
- `slide_files` 承载"一张片子多个路径"，死路径标 `missing_since` 而不是删
- 并发：WAL + `busy_timeout`，读写不再互斥（修复前实测 5.54 秒失败）
- `INSERT ... ON CONFLICT` 消掉注册竞态（修复前 8 并发有 3 个抛错）
- 新增 `hescope doctor`：文件在不在、pragma 对不对、schema 第几版、行数、悬挂引用、完整性、多少片子的文件已失效

**我认为缺什么**

1. **迁移还没跑。** 你库现在是 `version 0 of 3`。启动 app 只补了列和表，没写版本、没跑回填——所以 30 张片子的 identity 还是空的，`slide_files` 只有 1 行。
2. **重复内容的清理入口没有。** `dedupe-slides` 只有 `--dry-run`，**`--by-identity` 没实现**。你库里 5 行内容重复（slide 3/31 是同一张 demo，17/18/32 是另一组），它们的 identity 会永远为空。
3. **时间戳四套约定并存**，其中 `tcga_schema.py` 写 aware datetime 而 SQLite `DATETIME` 会**静默丢弃偏移量**。今天全对只因为所有写入方都在 UTC。

**后果**：1 是"好处还没兑现"；2 是"5 行片子拿不到 Phase 1 的任何好处"；3 是**定时炸弹**——错 8 小时且无异常，事后无法回溯。

**建议**：先跑 `migrate --dry-run` 给你看报告 → 你点头再执行（第 1 条）；时间戳统一是十几行，趁没出事做（第 3 条）；`--by-identity` 做工具+报告，执行权在你（第 2 条）。

## 2. 外部数据库接口 ○ —— 你一直在说、而它确实一行没做

**做到了什么**：`get_engine` 接受任意 SQLAlchemy URL；`HESCOPE_DB_URL` 环境变量生效。**仅此而已。**

**我认为缺什么**（全部实测）

| 承诺 | 实测 |
| --- | --- |
| README:230「换 PostgreSQL 只是一个环境变量」 | **驱动一个都没装**：psycopg2 / psycopg / pymysql / asyncpg 全无，`pyproject.toml` 里没有 db extra |
| 跨后端可用 | `init_db` 的升级路径用 `PRAGMA table_info`（SQLite 专有）；`INSERT ... ON CONFLICT` 在 MySQL 上语法不同；`SlideCatalog` 直接 `import sqlite3` |
| 读别人的切片库 | 只有本地文件和 DICOM 文件。**DICOMweb/PACS 没接**，尽管 `dicomweb-client 0.61.1` 已经装着（wsidicom 的硬依赖），`WsiDicom.open_web` 现成，**0 新增包** |

**后果**：一个已经有 Postgres 的实验室现在**装不上**；一个有 PACS 的医院**读不了**；一个有 QuPath 工程目录的人只能一个文件一个文件导。这三种恰恰是"用户已经有自己的数据库"的主要形态。

**建议**（按实测代价排序，前两条很便宜）：

1. **DICOMweb 读取** —— 0 新增包，`(scheme,key)=('dicomweb', study/series)` 身份已经支持
2. **文件夹 + 标签 CSV 导入** —— 除列映射外不需新代码，可能是最常见形态
3. **QuPath 工程目录** —— GeoJSON 解析器已有，缺的是"遍历工程"
4. **Postgres** —— 加一个 extra + 修三处 SQLite 假设 + 一个跳过式测试矩阵
5. OMERO —— 真新依赖，先量再说

## 3. ROI 的增删改 ◐

**做到了什么**

- **增**：画框 → Add ROI（08 轮修好，现在真进库）；Send to code agent（进库 + patch PNG + jsonl）；GeoJSON/ASAP 导入（10 轮接上，会如实报告跳过了什么）
- **删**：Annotations 面板选中表格行 → Delete ROI；**新增 `hescope delete-roi <id...>`**，默认只打印不删，`--yes` 才执行
- **查**：Statistics 面板、三个导出

**我认为缺什么**

1. **改：完全没有。** 不能移动、不能改形状、不能拖顶点。每次修正都是"删掉重画"。对要调边界的病理医生，这是工具和演示的区别。
2. **画布上删不了。** 但地基已经在了：`clicked_roi` 事件在 `osdviewer.py` 里发了 5 次、测试里 9 次、**`app.py` 里 0 次**。选中这个原语实现并测试过了，就差一个消费方。
3. **agent 不能删。** 契约里 `roi_delete` 只是个 interaction 类型，不是工具。agent 能建、能标，**不能删**——这个不对称在自主运行时会变成问题。
4. **改几何要连带失效的东西没定。** `rois.patch_path` 不是测量值，它是**训练输入**（`ml.py:252` 每次训练都读那个 PNG）。改了几何不让 patch 失效，就是拿旧像素训新标签。

**建议**：接 `clicked_roi` → 画布选中+删除（纯前端、无 schema 依赖、立刻能感到）；然后是移动/拖顶点；同时定下"几何变了，测量删除、patch 失效"这条规则。

## 4. 后端与性能 ◐

**做到了什么**：OpenSeadragon + 自建 DZI 瓦片服务，暖缓存单瓦片 **1 ms**；按需合成中间金字塔层；tile 缓存；三类后端（OpenSlide / tifffile-zarr / DICOM）。

**我认为缺什么**

1. **缩放一次 2.16 秒，而 0.43 秒的开关已经在代码里。** `HESCOPE_TILE_PARALLEL_READ=1` 实测 8 线程 **5.2×**，字节逐位一致。我没改默认值，因为只测了一个进程、一张片子、一个后端、单次——**下一步是基准工具，不是改默认**。
2. **合成层不落盘。** 18 层 DZI 只有 4 层来自文件，中间 14 层每次冷启动重算，而它们是确定性的。
3. **ROI 加载在 10³ 量级会痛**：100/1000/5000 个 ROI 是 3.6/48.8/138.4 ms，**每次重渲染全额支付**。导入一个 QuPath 工程就是这个量级。修法不是缓存，是视口查询（bbox 列已经加好了，查询还没写）。

## 5. 前端信息架构 ◐

**做到了什么**：侧栏（打开/显示/导航图/ROIs）+ viewer + 状态栏 + 五个手风琴。08–10 轮修掉了六条"界面说的和事实不符"。

**我认为缺什么**

1. **agent 在界面里没有存在感。** 如果 agent 在自主分析，你看不到它在做什么、发现了什么，**也没法叫停**。这是最大的缺口，而且**不需要任何 schema 改动**——`interactions` 表已经记录了每一次 agent 调用、带 actor。
2. **五个分析面板默认全折叠。** 这条我给的是**观察不是建议**——它取决于你实际看片的流程，只有你能判断。
3. **"Zoom to fit" 并没有 fit** —— 实测它框住 81,671 px 里的 54,471 px，而滑块够不到能真正 fit 的那档。
4. **侧栏没有消息区**，侧栏按钮的回话出现在主区域。

## 6. AI / agent 通道 ●

**做到了什么**（本次会话端到端验证过）

- `marimo edit --mcp code-mode` → `/mcp/server`，`list_sessions` + `execute_code`
- 9 个模块级 agent 工具，**零点击**读取你正在拖的 ROI（level-0 坐标、bbox、mpp、切片元数据）
- `marimo._code_mode`：agent 可以往运行中的 notebook **写新 cell 并执行**，且是持久的
- agent 落盘交接：`agent_out/patches/*.png` + `roi_history.jsonl`

**我认为缺什么**

1. **agent 的写入面太窄**：能标签，不能删、不能记录自己算出的测量值、不能按指定分辨率要一块 patch。
2. **exploration 会污染产品。** agent 建的 cell 就是对 `app.py` 的永久修改——marimo 的 autosave 已经在本次会话里**悄悄回滚过一个已提交的修复**。需要"探索 notebook + 晋升路径"这个结构。
3. **`annotate_roi` 会丢掉自己的结果**：它调 `update_annotation` 却丢弃返回的 bool（那个 bool 正是 07 轮为"分辨 no-op 与真写入"加的），实测能返回没有任何文档写过的裸 `'null'`。

## 7. 分析栈可信度 ○ —— 我认为这是全局最严重的一条

**做到了什么**：细胞核检测、H&E 反卷积、4 种染色归一化、56 维特征、全片热图扫描、弱监督训练、QC 报告、病理基础模型编码器工厂（按 license 门控）。

**我认为缺什么** —— 不是功能缺，是**每个数字都不带它成立的条件**：

| max_size | 有效 mpp | 核数 | density/mm² |
| --- | --- | --- | --- |
| 256 | 3.889 | 167 | 201.5 |
| 2048 | 0.485 | 4904 | **5927.3** |

**同一块组织、同一个 ROI，29.4 倍。** 一个随提取参数变 29 倍的"每平方毫米密度"不是组织的属性，是栅格的属性。

另外两条同源的：`blur_score` 随同一参数变 6.72 倍；全片扫描用的 `tissue_fraction_proxy` 在 `roi_stats` 判 0.74 的区域返回**饱和的 1.0000**——**扫描和逐 ROI 测量测的不是同一个量**。

而且 `SELECT avg(tissue_fraction) FROM rois` 到今天仍然是 `OperationalError`——测量值全在 JSON blob 里。

**建议**：这条**单独立项**，不要顺手做。而且正确解法不是"加一列 mpp"——记录分辨率只让你能**察觉**不可比，**不能让数字变得有意义**。正确解法是每个 skill 声明**实测的有效分辨率区间，越界拒绝执行**。这需要你（真正看片的人）参与定义什么算有效。

# 我的排序建议

| 批次 | 内容 | 为什么在这批 |
| --- | --- | --- |
| **现在** | 跑迁移（先 dry-run 给你看）· 时间戳统一 · `clicked_roi` → 画布删除 · agent 状态条 | 都小，且前两条是"趁没出事" |
| **接着** | DICOMweb（0 包）· 文件夹+CSV · `dedupe-slides --by-identity` · 视口 ROI 查询 · tile 基准工具 | 外部接入的主力，代价都已量过 |
| **然后** | ROI 编辑（移动/顶点）· Postgres extra · QuPath 工程 | 需要更多设计 |
| **单独立项** | 测量值与有效区间 → 然后才是 skill 与 LoopX | 需要你参与定义 |

**你现在说先做数据库，那第一批里属于数据库的就是：跑迁移、时间戳、`--by-identity`，加上第二批的 DICOMweb 和视口查询。** 外部接口（第 2 节）是这里面最实质的欠账。
